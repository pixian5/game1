# 01 · 架构与代码约定

> 来源：v0.1.7 模块化拆分、v0.1.13 PWA 修复、build_bundle 相关文档、check_version.js 实现

## 一、零构建是硬约束

浏览器直接加载 `index.html` 里列出的 **68 个 `<script src>`**，没有打包器、没有模块系统、
没有 `import`/`export`（除了 `story/` 下的数据文件用了 ES Module 语法，由构建脚本剥离）。

**为什么重要**：任何"顺手引入一个 npm 包"的想法都会破坏这个前提。
新增第三方能力必须自己用原生 API 实现（例如音频用 WebAudio 合成，不用音频库）。

## 二、模块分层与加载顺序

```
story/       18 个纯数据板块，只有数据没有逻辑
engine.js    核心引擎（状态机、时间推进、事件调度）
engine_*.js  原型混入（social / content / progress / save / domains）
ui/          25 个界面文件，共享同一个全局词法作用域
audio.js     WebAudio 合成
i18n/        语言包
```

**关键陷阱**：`ui/` 下的文件**共享全局作用域**，所以它们之间可以直接互相调用函数，
但这也意味着：
- 函数重名会静默覆盖，不报错
- 加载顺序错会导致 `undefined is not a function`
- 新增 ui 文件必须同时改 `index.html` 和 `tools/build_bundle.mjs`（后者按 index.html 顺序合并）

## 三、版本号必须五处同步

唯一来源是根目录 `VERSION` 文件，但实际有五个地方要一起改：

1. `VERSION`
2. `package.json` 的 `version`
3. `package-lock.json`（两处）
4. `index.html` —— 标题、`<meta name="version">`、以及**全部 69 处 `?v=` 查询串**
5. `sw.js` 的 `CACHE_VERSION`

**正确做法**：永远用脚本改，不要手工。

```bash
python3 tools/bump_version.py 0.9.7
node check_version.js   # 自检
```

`check_version.js` 会核对上面五处，包括数 `?v=` 的出现次数。
漏改一处，Service Worker 会继续命中旧缓存，线上表现就是"改了代码但没生效"。

## 四、Service Worker 缓存链

`sw.js` 的 `CACHE_VERSION` 和 `?v=` 参数是两套机制，必须同时更新：

- `?v=` 控制浏览器 HTTP 缓存
- `CACHE_VERSION` 控制 Service Worker 的预缓存

**踩过的坑（v0.1.13）**：PWA 离线模式曾经完全不可用，
原因是预缓存清单里的资源路径与 `index.html` 实际引用的不一致。
改完资源清单后一定要在 DevTools 里切到 Offline 模式实测一次。

## 五、发布产物必须用 dist

根目录当站点根，浏览器会串行请求 68 个脚本（实测首屏 18.4 秒）。
用 `node tools/build_bundle.mjs` 合并成单 `bundle.js` 后降到 3.5 秒左右。

```bash
node tools/build_bundle.mjs
# dist/bundle.js     约 801KB
# dist/index.html    单脚本引用
# dist/sw.js         预缓存已对齐
# dist 总体积        约 3.85MB
```

构建脚本会做三件事：按 index.html 顺序合并脚本、剥离 story 文件的 import/export、
重写 dist/index.html 为单 script 引用并对齐 dist/sw.js 预缓存。

## 六、修改代码后的固定动作

```bash
npm run test:all      # 版本校验 + 剧情校验 + UI 校验 + lint + 回归 + 剧情链 + 浏览器 E2E
node tools/build_bundle.mjs
```

`test:all` 里任何一环失败都不要继续往下做，先修好。
