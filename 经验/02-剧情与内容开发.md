# 02 · 剧情与内容开发

> 来源：v0.1.9 / v0.1.10 内容补齐、v0.9.2-v0.9.6 内容与可达性、三线通关实测结论

## 一、事件数据结构要点

事件都是数据对象，关键字段：

```js
{
  id: 'xxx',                    // 全局唯一，测试会查重
  trigger: { day: 4, hour: 9 },  // 时间触发
  // 或 trigger: { event: '某事件id', dayFallback: 5 }  事件触发 + 天数兜底
  // 路线过滤：trigger.soloOnly: true / trigger.inRoute: 'shenyan' 等
  messages: [...],              // 消息批次
  choice: { options: [...] },   // 选择
}
```

**选择项跳转**用 `choice.options[].effects.thenEvent`，
消息批次之间用 `message_batch` 的 `then` 链式串联。

## 二、时间推进机制

- `advanceTime(minutes)`：按分钟推进，**每次地点移动 +30 分钟**
- `advanceToNextDay(hour)`：直接跳到次日某点（玩家点"等到明天"时用）
- `_checkTimeEventsForRange`：补触发被睡眠跳过的小时
  —— 没有它，玩家一觉睡过去就会永久丢失触发窗口

**开发时最容易忽略的**：写了一个 `trigger: {day: 5, hour: 14}` 的事件，
如果玩家那天 13:00 睡到 18:00，靠 `_checkTimeEventsForRange` 才能补上。
但补触发仍然是"发现窗口被跳过"，不是"任何时候都会触发"。

## 三、内容可达性 —— 本项目最大的坑

**实测结论（2026-11-18 三线完整通关）**：结局在 **day8-10** 触发，
但 day11-21 新增了大量事件，**大部分根本走不到**。

原因：
1. 结局触发后 `gameEnded` 置位，后续时间事件全部不再调度
2. 路线专属事件写了 `trigger.inRoute`，但选了路线后玩家可能在别的日子就进了结局分支

**做内容前必须先算清路线长度**。判断一个新事件是否可达，按这个顺序查：

```bash
node tools/reachability.mjs    # 输出不可达事件清单
```

自查清单：
- 该事件 `trigger.day` 是否 ≤ 结局触发日？
- 如果是路线专属，该路线的玩家在这个 day/hour 是否还"活着"（没进结局）？
- 它与主线路链是否会在消息队列里抢时序？

**踩过的坑**：曾经想在 day4-6 补 14 条"空窗期"事件，
结果与南方出差/告白/危机/雨夜回程的路线链冲突，一次性挂掉 5 个剧情测试
（雨夜回程、半个月后、结局触发、游戏已结束、已记录结局）。
**结论：day4-6 根本没有空窗期，别往那儿塞。**

## 四、路线与调度隔离

v0.9.5 做的核心改造是**调度隔离**：线内事件移入"选线后窗口"，
避免未选线时就被调度、或者在错误的路线上触发。

路线专属事件写法：
- `trigger.soloOnly: true` —— 只有独行线可见
- `trigger.inRoute: '<路线id>'` —— 指定路线可见

改调度逻辑后**必须重跑 `npm run test:story`**（294 条断言），
这条链专门检测时序问题。

## 五、独行线内容偏薄

当前统计：沈砚之/陆辞/江屿各 6 条路线专属时间事件，**独行线只有 1 条**
（另有 17 个 `soloOnly` 链式事件）。

这是已知的内容短板，做内容扩张时优先补独行线。

## 六、每日事件密度不均

现状（v0.9.5 统计）：

```
day4: 5  day5: 5  day6: 6  day7: 8  day8: 5  day9: 6
day10: 2  day11: 8  day12: 3  day13: 4  day14: 3
```

day10 只有 2 条、day11 有 8 条，落差明显。
`validate:story` 还会警告 **day5 时间事件仅 1 条**（建议 ≥2）。

## 七、内容提交前必做

```bash
node validate_story.js      # 错误必须为 0
node test_story.js          # 294/294
node tools/i18n-gap.mjs     # 新增文案是否都补了英译
node tools/reachability.mjs # 新增事件是否可达
```

四个都过再提交，否则会留下难以追溯的时序问题。

## 八、同一会话的选择会同时挂着：必须排队（v0.9.11）

**规则：任何地方都不要直接写 `conv.pendingChoice = xxx`，一律走 `engine._setPendingChoice(会话或群, 选择)`。**

背景：引擎投递带选择的消息时，如果会话里已经挂着没回复的选择，旧实现直接覆盖，
旧选择的后续事件永远不派发。v0.9.11 改成排队：

- 一个会话同一时刻只亮出一个选择，后到的进 `choiceQueue`，前一个被回复后下一个自动亮出
  （`_promoteNextChoice`，延迟 700 毫秒发出通知，避免被界面点击处理末尾的「收起选项条」清掉）
- 队列顺序固定：**普通选择在前、邀约在后**。邀约有 120 秒真实时限，是支线，不能堵主线
- 邀约有结果（赴约 / 拒绝 / 超时）时必须调 `_purgeInvitationChoice` 清掉残留选择，
  否则「僵尸邀约」会把后面的主线选择一直堵住
- `choiceQueue` 在存档白名单里（`engine_save.js` 的 `sanitizeChoiceQueue`）；
  新增会话上的持久化字段时记得加白名单，否则读档就丢

修复前的实测（4 条路线 × 5 种回复节奏，共 20 次运行）：40 次选择被静默丢掉，
6 次运行永远到不了结局——隔 2 个游戏小时回复的玩家江屿线卡死，隔 24 小时回复的玩家四条线全卡死。

**排查命令**：`node tools/choice_override_probe.mjs`（已挂进 `test:all`）。

## 九、内容可达性取决于玩家节奏（修正旧结论）

旧文档说「day11–21 的内容结构性不可达」。**这个结论只对「看到选择立刻回复」的玩家成立。**

真实情况：结局在剧情链走完时立刻触发，剧情链走多快取决于玩家回复多快。

| 回复延迟（游戏小时） | 带日期事件的触达率 | 结局日（沈 / 陆 / 江 / 独） |
|---|---|---|
| 0 | 29% | day7 / day7 / day9 / day8 |
| 2 | 50% | day9 / day9 / day13 / day10 |
| 6 | 58% | day10 / day12 / day14 / day11 |
| 12 | 73% | day13 / day14 / day16 / day13 |
| 24 | 85% | day15 / day17 / day19 / day15 |

对任何节奏都触达不到的只有 10 条：男主线尾段 4 条（`jiangyu_call_bside`、`day19_route_msg`、
`day20_route_city`、`day21_route_month`）与独行线尾段 6 条（day16–21 的 soloOnly 事件）。

**解法实测**：引擎已有开关 `STORY.finaleGate`（`story/04_route_ending.js`，默认 `null`），
含义是「路线主线最早从第几天才开始」。对比实验（每组 20 次运行）：

| 门槛 | 触达率（立刻回复 → 延迟 24 小时） | 快慢落差 |
|---|---|---|
| 不设 | 29% → 85% | 57 个百分点 |
| 11 天 | 71% → 85% | 14 个百分点 |
| 12 天 | 77% → 85% | 8 个百分点 |
| 13 天 | 82% → 87% | 5 个百分点 |

设 12 天时，**day4–13 的 54 条带日期事件对任何节奏的玩家都是 100% 触达**。

复现：`node tools/choice_override_probe.mjs --finale-gate=12 --max-day=40 --delays 0,2,6,12,24 --json`

## 十、触发条件的六个字段（写事件时对照）

剧情里 `trigger` 实际只用到这六个字段，语义以 `engine.js` 的 `checkTimeEvents` 为准：

| 字段 | 含义 |
|---|---|
| `day` / `hour` | 哪一天的哪个整点触发（跨小时会被范围补扫补上） |
| `route` | 只在这条路线触发（`shenyan` / `luci` / `jiangyu` / `solo`） |
| `soloOnly: true` | 进入男主线后不再触发（未选线时和独行线可见） |
| `inRoute: true` | 只在任意一条男主线内触发 |
| `deferWhenBusy: true` | 主线忙时延后派发（最多延 15 秒真实时间）；带它的 22 个事件的选择也都是 `auto: true` |

注意 `inRoute` 的值是布尔值 `true`，不是路线编号。写分析脚本时如果把它当字符串比较，
会把这 7 条事件误判成「永远不可见」（2026-11-24 踩过）。
