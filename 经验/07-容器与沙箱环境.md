# 07 · 容器与沙箱环境

> 来源：v0.9.0 容器交接、容器接手须知、本轮 Instabox 核对与升级实测

## 一、本机 ≠ 服务器，绝不能混用

用户的本机是 **MacBook M5 芯片、macOS 27**。服务器和沙箱是 Linux。
以下事情在本机能做、在容器里不能（或反之）：

| 事项 | 本机 | 容器/沙箱 |
|---|---|---|
| `brew install` | 可以 | 没有 brew |
| 启 Docker | 可以 | 通常不行 |
| 图形界面 / 截图 | 可以 | 不行（用无头浏览器） |
| 访问本机 `127.0.0.1` | 可以 | 是容器自己的回环 |

**Python 依赖绝不能装在系统环境**：本机用 `uv` 虚拟环境，
一次性工具用 `uvx`。项目里的 Python 脚本要先检查项目内是否有虚拟环境，
没有就创建并激活，然后再跑。

## 二、Instabox 沙箱的基本事实

- 命令行工具安装：`curl -fsSL https://instabox.sh/install.sh | sh`
  或 `npm install -g instabox`。**不是 pipx。**
- 认证二选一：
  - 交互登录 `instabox login`
  - 环境变量 `INSTABOX_API_KEY=ibk_...`（给其它 AI 用时用这个，无需扫码）
- 沙箱默认 4 vCPU / 8 GB，空闲 30 分钟自动暂停
- 免费套餐只能用 `agent-browser` 模板
- 常用命令：
  ```bash
  instabox ls
  instabox exec <沙箱> -- "<命令>"
  instabox exec <沙箱> --background --cwd <目录> -- "<命令>"
  instabox port publish <沙箱> <端口>
  instabox port ls
  ```

**`instabox push ./dir --dir` 有坑**：实测会推 0 个文件。
绕过方法是先 `tar czf` 再推压缩包，进去解压。

## 三、沙箱里的环境差异

实测本项目的沙箱环境：
- git 2.47.3、Node.js v22.23.3、Python 3.13.5
- 磁盘 `/data` 20 GB
- **没有 npm 依赖**（`npm install` 在容器里可能因镜像源策略失败）

**好消息**：`tools/build_bundle.mjs` 是零依赖的构建脚本，
不需要 `npm install` 就能跑。这是当初有意设计的，就是为了容器里能构建。

本机安装 Playwright 依赖时遇到过 `EALLOWREMOTE` 错误（npm 12 的镜像源策略），
解决方式是 `npm install --allow-remote=all`。

## 四、沙箱里的仓库不一定干净

**这是本轮踩到的真坑**：`/data/home/game1` 里有 **16 个文件的未提交本地改动**
（`i18n/en-US.js`、`i18n/zh-CN.js`、`index.html`、`sw.js`、`ui/` 下多个文件等）。

如果接手的 AI 直接 `git reset --hard origin/main`，这些改动会被**静默丢弃**。

**正确做法**：
1. 先打包备份 `tar czf game1-backup-$(date +%Y%m%d%H%M).tar.gz game1`
2. **重新克隆到新目录**（例如 `game1-new`），原目录保持不动
3. 在新目录构建，产物放独立站点根（例如 `/data/home/site`）
4. 只停本项目端口的进程，重启服务
5. 验收通过后才把旧目录改名留档，不要直接 `rm`

## 五、共享资源意识

一个沙箱可能同时跑多个项目。动手前先看：

```bash
ps aux | grep http.server
ss -lntp | grep -E ':(8080|9090)'
readlink -f /proc/<pid>/cwd     # 确认某个进程服务的是哪个目录
```

确认清楚"哪个端口属于谁、哪个进程的工作目录是什么"再动手。
本项目的实践结论写在 `经验/06-部署与运维.md` 的端口表里。

## 六、给其它 AI 的交接提示词要点

1. **先核对再动手**：先 `instabox ls` 判断是否已部署，已部署就只做核对
2. **不删除沙箱、不删除线上产物**
3. **不动别人的端口**
4. **只发 dist**
5. **版本号用 `tools/bump_version.py` 改**
6. 完整模板见 `docs/deploy-handoff-instabox.md`（含真实令牌，在 `.gitignore` 里）

## 七、当前 vefaas 容器（2026-11-20）实测

- 项目在 `/home/user/code/game1`，Node v22.23.4；系统无 Chrome，Playwright 默认内核缺失。
- Playwright 实际可用浏览器：`$HOME/.cache/ms-playwright/chromium-1243/chrome-linux64/chrome`，
  启动需 `--no-sandbox`；1.61 默认期望 `chromium_headless_shell-1228`，会报 “Executable doesn't exist”。
  正确命令：
  `PW_CHANNEL=none PW_EXECUTABLE_PATH=$HOME/.cache/ms-playwright/chromium-1243/chrome-linux64/chrome npm run test:account`
- 账号服务跑在 `0.0.0.0:8095`，DB `server/data/game.db`；`8080` 是 AIO Sandbox，不要占。
- 本机 `8079` 是端口反代（`server_name ~^(?<port>\d+)-(.+)$`）。公网域名是
  `<port>-<实例ID>.instabox.tech`，但当前容器端口未在平台侧“发布”，直接访问会返回
  “This URL is not published”；容器内用 `127.0.0.1:8095`，公网需平台端口发布或独立服务器。
- 容器不持久：所有成果必须 commit + push；数据库/日志要单独备份。

## 八、Instabox 沙箱会被改名复用（2026-11-20 实测）

同一个沙箱实例（ID `m_agqxoy6u363jxgfufg2onqxbm4`）先后被命名为
`box-c6119b` → `xjp`。**判断沙箱身份要认 ID 不认名字**。
交接文档里的沙箱名会过时，`instabox ls` 的输出才是准的。

同时 9090 端口的服务形态也会演进：v0.8.5/v0.9.6 时代是
`python3 -m http.server 9090`（纯静态），v0.9.9 起改为
`node server/index.mjs`（静态 + 账号 API 同源一体化，`NH_SITE_ROOT` 指向项目根）。
重启服务前必须先 `ss -lntp | grep 9090` 确认现在是谁在服务，
不能凭旧文档记忆直接 `pkill -f 'http.server 9090'`。

## 九、Node http 回调里的同步异常会杀死整个进程（v0.9.10 教训）

`server/index.mjs` 曾在 `serveStatic` 里裸调 `decodeURIComponent(url.pathname)`，
`curl /%` 一个请求就抛 URIError → uncaughtException → 进程退出，
所有用户登录态不可用。**修复分两层**：

1. 精确层：对请求路径的解码/解析一律 try/catch，失败返回 400；
2. 兜底层：进程挂 `uncaughtException` / `unhandledRejection` 处理器，只记录不退出。

Instabox 网关会拦截畸形 URL，所以线上实测打不崩——
**但网关拦截不是代码安全的依据**，部署到直连环境就会暴露。

## 十、多 AI 并发部署冲突实录（2026-11-20 19:56 实测，必读）

本轮升级 Instabox 到 v0.9.10 时，另一个 AI **在同一分钟内**也在向同一沙箱部署：

- 我按豆包文档把 `game1-v099` 升到 v0.9.10、替换 `/data/home/site`；
- 对方同时在 `/data/neon-heart` 部署自己的 v0.9.9（双端口 8081+9090，
  自带 `serve-loop.sh` 守护循环自动拉起进程）并抢占 9090；
- 我 `pkill` 的是自己的旧进程，新服务却因端口被占 EADDRINUSE 启动失败。

**排查口诀**：端口被占先查"谁在占"再动手——

```bash
ss -lntp | grep <端口>                    # 找到 pid
ps -p <pid> -o cmd                        # 是谁的什么服务
tr '\0' '\n' < /proc/<pid>/environ | grep NH_   # 它的部署参数（端口/站点根/数据库）
```

**处置原则**（本次实际采用，零破坏）：
1. 认 ID 不认名字，认端口不认目录——先弄清对方部署结构再动；
2. 读 `/proc/<pid>/environ` 拿到对方的 NH_SITE_ROOT / NH_DB，
   **保留对方的部署位置和数据库**，只升级版本内容；
3. 发现 `serve-loop.sh` 守护循环后，杀进程即自动拉起新代码，
   不需要（也不应该）手动 nohup 抢端口；
4. 动手前 sudo 备份对方目录（本次 4.3MB）并查看数据库行数确认风险；
5. 升级完成后立刻推送 git + 更新交接文档，让其它 AI 看到新基线，
   避免它再按旧文档部署回去。

**根因**：多 AI 各自持有过时的部署认知 + 没有部署锁。
长期解法：部署前先 `git pull` 看最新交接文档 + 在 docs 里写部署日志（对方做了），
发现冲突时以"线上正在服务者优先，版本低的一方升级内容而非抢端口"。

## 十一、沙箱又改名了：命令里用实例编号（2026-11-24）

同一个实例（编号 `m_agqxoy6u363jxgfufg2onqxbm4`）的名字先后是 `box-c6119b` → `xjp` → `sbjp`。
用旧名字执行 `instabox exec xjp` 会直接报「没有这个沙箱」。

**命令里一律写实例编号**：

```bash
instabox ls --json                                   # 先看现在的名字和编号
instabox exec m_agqxoy6u363jxgfufg2onqxbm4 -- "<命令>"
```

用环境变量认证（用户在全局指令里给的密钥）：`export INSTABOX_API_KEY=ibk_...`。
只读核对时看这几项：`ss -lntp`（谁在监听）、`/proc/<进程号>/environ`（它的启动参数）、
`crontab -l` 与 `systemctl --user list-timers`（有没有定时任务）、数据库各表的行数。

沙箱里可能同时跑着别人的进程（例如 `/app/server/index.mjs`，文件名碰巧相同但属于别的用户，
读它的环境变量会报权限不足）。**只动 `/data/neon-heart` 和 `/data/home` 下我们自己的东西。**

沙箱元信息里写着最长连续运行 480 分钟、空闲自动暂停，本质上是临时环境，
不要把它当作长期的唯一入口。

## 十二、沙箱上现在有三样由 systemd 用户会话管理的东西（2026-11-24）

| 单元 | 作用 | 位置 |
|---|---|---|
| `neon-heart.service` | 游戏与账号服务（托管 `serve-loop.sh`，监听 8081） | `~/.config/systemd/user/`，即 `/data/home/.config/systemd/user/` |
| `neon-heart-backup.timer` | 每天备份数据库 | 同上 |
| （依赖）用户级服务管理器 | 开机启动上面两个，前提是 `loginctl enable-linger x` | — |

常用命令（都在沙箱里执行，通过 `instabox exec <实例编号> -- '…'`）：

```sh
systemctl --user status neon-heart.service          # 游戏服务状态
systemctl --user restart neon-heart.service         # 重启游戏服务
systemctl --user list-timers --all                  # 备份定时器下次什么时候跑
journalctl --user -u neon-heart.service -n 30       # 守护脚本的输出
tail /tmp/neon-server-8081.log                      # 服务进程的访问日志
```

重启游戏服务仍然可以用老办法 `sudo fuser -k 8081/tcp`。

**沙箱里能跑浏览器端到端**：有系统自带的 Google Chrome，`npm install` 能装上测试依赖。
所以依赖数据库的测试（账号接口、账号端到端）放在沙箱上跑：

```sh
npm run test:db:instabox          # 在本机执行；默认只跑账号接口测试
npm run test:db:instabox -- all   # 再加账号端到端
```

它在沙箱里重新克隆 main 到 `/data/home/game1-dbtests` 再执行，不动 `/data/neon-heart` 上的线上站点。

**沙箱里的 `bc` 没有安装**，需要算时间差时用 `date +%s` 取整数秒，或者干脆数探测次数。
