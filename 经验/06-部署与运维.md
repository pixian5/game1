## 三、自有服务器的历史坑

- **nginx 监听 9443**，因为 80/443 被服务器上既有的代理服务占用了，**不可触碰**
- **`add_header` 不继承**：在某个 `location` 里写了 `add_header`，
  父级的其他 `add_header` 会全部失效，必须在该层重写完整
- **`deploy.sh` 的清单必须与 index.html 的依赖一致**：
  早期漏了 `i18n/` 和 `privacy.html`，线上直接 404
- **`rsync --delete` 有风险**：源目录不全时会删掉线上文件
- 证书用 acme.sh 的 DNS-01 方式，自动续期

## 四、CDN 缓存滞后

GitHub Pages 改完 `gh-pages` 分支后，CDN 仍可能提供旧版本 10-15 分钟。
判断方法：直接看 `gh-pages` 分支内容是否已更新，
如果分支对了但线上还是旧的，就是 CDN 问题，不要反复改代码。

**用 bundle 哈希比对而不是只看页面能否打开。**

## 六、凭据管理

**含真实令牌的文档绝不能进仓库。** GitHub 有 Push Protection，
一旦推上去会被直接拦截（GH013），而且令牌已暴露在传输过程中。

正确做法：
1. 凭据文档写入 `.gitignore`
2. 需要给其它 AI 时，通过对话传递，不要靠仓库
3. 长期方案是模板 + 环境变量注入

当前的凭据文档：`docs/deploy-handoff-instabox.md`、`docs/deploy-handoff-prompt.md`，
两者都已在 `.gitignore` 里。

### 凭据必须实测验证，不能只靠抄

**血泪教训（2026-11-19）**：旧交接文档里的 SSH 私钥抄错了一个字符
（第 4 行 `dzAsK/3g` 应为 `dzAsp/3g`），base64 肉眼完全看不出来，
但密钥直接不可用。同批还发现 Hugging Face 令牌已返回 401 失效，
而文档里仍写着"可用"。

**写入凭据后的强制验证清单**：

```bash
# 1. Git 平台令牌：实际 ls-remote 一次
GIT_TERMINAL_PROMPT=0 git ls-remote https://用户名:令牌@域名/路径.git -h refs/heads/main

# 2. Instabox 密钥
INSTABOX_API_KEY=ibk_xxx instabox whoami

# 3. Hugging Face 令牌
curl -H "Authorization: Bearer hf_xxx" https://huggingface.co/api/whoami-v2

# 4. Cloudflare 令牌
curl -H "Authorization: Bearer cfut_xxx" https://api.cloudflare.com/client/v4/user/tokens/verify

# 5. SSH 私钥：能派生公钥就说明格式内容都对
ssh-keygen -y -f 提取出的私钥文件
diff 提取出的私钥 原始私钥文件      # 逐字节比对
```

每一条都要把**实测结果（可用 / 已失效）写进交付文档**。
写着"可用"但实际失效的凭据，会让接手的 AI 浪费大量时间排查，
比不提供凭据更糟。

## 七、GitHub Push Protection 的长期影响

GH013 拦截的是**整条历史**。即使后来把文件 `git rm --cached` 并从工作树删除，
只要历史提交里还有令牌，推送仍会被拒。

实测状态：GitHub main 停在 `b68ea33`，其它三个远端已到 `a417238`。
**代码本身无差异**（差的都是含凭据的文档提交），因此接受这个状态，
不做 force push 改写历史。

`gh-pages` 分支不含那些历史提交，**可以单独正常推送**。

## 八、gh-pages 分支容易被污染

实测发现该分支曾经有 **68MB**：包含 `node_modules`、`coverage`、`qa-shots`、
`test-results`、`.freebuff` 等开发垃圾，而且**缺少 `.nojekyll`**。

`gh-pages` 分支**只应该放 dist 的内容 + `.nojekyll` + `.gitignore`**。
缺 `.nojekyll` 会让 GitHub Pages 走 Jekyll 处理，下划线开头的资源可能 404。

更新方式是干净的 orphan 提交或直接把内容清空后复制 dist，不要增量叠加。

## 七、多远端一致性检查

当前可用的远端（AtomGit / GitCode / GitHub；本仓库当前未配置远端）：

```bash
for r in atomgit gitcode origin; do
  echo -n "$r: "; git ls-remote $r -h refs/heads/main | head -1
done
```

推送用 `bash push_all.sh`（纯 ASCII 输出，曾因多字节字符出过 `unbound variable`）。
**GitHub 因为令牌文档被拦，会比其它三个少几个纯文档提交，代码无差异，可接受。**

## 九、可选账号服务的部署（v0.9.9）

账号服务与游戏同源，一个 Node 进程同时发静态和 `/api`，不需要 CORS：

```bash
cd /home/user/code/game1
server/ctl.sh start|stop|restart|status|logs
node server/backup_db.mjs        # VACUUM INTO 一致性备份
```

铁律：
- Node 必须是 **22+**（依赖内置 `node:sqlite`，不要 `npm install sqlite3`）
- `server/data/` 必须 gitignore：DB、WAL、日志、PID、备份都不能入库
- 静态服务必须把 `server/ docs/ tools/ 经验/ .git/ node_modules/` 等目录 404 掉
- HTTPS 终结在网关时，要把 `X-Forwarded-Proto` 传进来，否则 Cookie 不会带 `Secure`
- 公网部署时 `NH_SITE_ROOT` 指向 `dist`，但 `server/` 仍要在 Node 侧、不能进静态根

容器端口代理：本机 `8079` 的 `<port>-*` 反代按 Host 前缀取端口，
`curl -H 'Host: 8095-localhost:8079' http://127.0.0.1:8079/api/health` 可本地验证。

## Instabox：把静态站升级为 Node 同源服务（v0.9.9 实测）

- 沙箱自带 Node v22.23.3，`node:sqlite` 可用（有 ExperimentalWarning，不影响运行）。
- 纯 `python3 -m http.server` 只能发静态，账号卡片会显示“服务不可用”；
  换成 `server/index.mjs`（同端口发静态 + `/api`）后账号功能零改动可用。
- 启动三要素：`NH_PORT=9090`、`NH_SITE_ROOT=<站点根>`、`NH_DB=<仓库外路径>`。
- **必须把 `VERSION` 复制进站点根**，否则 `/api/health` 的 `version` 是 `unknown`。
- 停旧进程务必写 `pkill -f 'http.server 9090'`，同沙箱 8080 可能是别人的项目。
- 替换站点根用「先 `mv site site.old-时间戳` 再 `mv site.new site`」，失败可秒回滚。

### 持久分区与数据迁移（Instabox）

- 部署和数据只放 `/data`（vdb 数据盘）；`/` 是系统盘，沙箱重建会重置。
- 本项目持久目录：`/data/neon-heart`，守护脚本 `serve-loop.sh`（退出自动拉起）。
- 迁移 SQLite 库**不要直接 `cp`**：WAL 模式的最新写入在 `-wal` 文件里，先
  `PRAGMA wal_checkpoint(TRUNCATE)`，或使用 `server/backup_db.mjs` 的 backup API。
- 两个端口可以共用同一 `game.db`（WAL 支持多进程），但迁移/备份时必须先停写或 checkpoint。
- 迁移后必查 `users / sessions / saves` 计数，避免把测试账号带上线。

### 一个项目只保留一个对外入口

- 同一份数据库可以同时被多个端口服务，但浏览器按域名隔离 Cookie：
  `8081-xxx` 与 `9090-xxx` 是两个站点，登录态不共享，用户会以为账号丢了。
- 收敛为单入口（本项目 8081 + `serve-loop.sh` 守护）；需要临时备用入口时再手动起，
  用完即停，不要长期双活。

## 凭据进了公开仓库的历史（2026-11-24 发现，最高优先级）

提交 `9433d26` 里的 `docs/deploy-handoff-prompt.md` 含 15 处密钥内容：服务器 SSH 私钥、
GitHub 令牌、Cloudflare 令牌、Gitee 令牌、GitCode 令牌、抱脸令牌。
后来文件从工作区删掉了，但**历史提交里还在**，而 GitCode、Gitee、GitHub 三个仓库
都可以不带令牌匿名读取——任何人都能执行 `git show 9433d26:docs/deploy-handoff-prompt.md`。

GitHub 的推送保护（GH013）拦的是「把含密钥的提交推上去」这件事，所以 GitHub 上还没有；
另外两个平台的历史里已经有了。**不要去点 GitHub 给的「放行」链接**，那等于多一个泄露点。

处理顺序（需要用户决定）：
1. 用户先更换全部密钥（SSH 密钥对、Cloudflare、GitHub、Gitee、GitCode）；
2. 再用 `git filter-repo` 把文件从全部历史里抹掉，强推所有远端；
3. 通知所有协作者重新克隆。

**以后的规矩**：含令牌的文档只存本地并放进 `.gitignore`（现在是
`docs/deploy-handoff-instabox.md` 与 `docs/deploy-handoff-prompt.md`）；
凭据通过对话交接，不进仓库。提交前确认：
`git diff --cached --name-only | grep -iE "deploy-handoff|credential|\.env"` 必须为空。

## 改写 Git 历史的做法（2026-11-24 实战）

上面「凭据进了公开仓库的历史」一节的问题已按下面的流程处理。步骤固定，照做即可：

1. **先备份旧历史**到仓库之外，并校验备份完整：
   `git bundle create <仓库外路径> --all && git bundle verify <同一路径>`（权限设成 600；
   备份本身含旧凭据，密钥更换后可以删）。
2. **先扫全历史，别只处理已知的那一个提交**。这次除了已知的交接文件，还查出另一份文档的旧版本
   在 62 个提交里带着 Gitee 令牌。扫描方法：对每个提交执行 `git grep -l -E "<令牌模式>" <提交> -- .`。
   令牌模式要分开写、写简单些：本机的 grep 对复杂正则有上限，会直接报错（报错时输出是空的，
   很容易误以为「没有命中」）。
3. **在全新的临时克隆里改写**，不动工作区。工具用 uvx 调起，不往系统里装东西：
   `uvx --from git-filter-repo git-filter-repo --force --prune-degenerate never --path <要整个移除的文件> --invert-paths --replace-text <替换清单>`
   替换清单每行一条：`字面量==>***REMOVED***`。只清理某几处的文件用替换，不该进仓库的文件整个移除。
4. **改写后必须逐项校验，再强推**：
   - 当前文件树哈希与改写前一致（`git rev-parse HEAD^{tree}`）；
   - 全历史令牌扫描为 0；
   - 按提交说明与时间把新旧提交配对，差异只允许出现在被清理的文件上；
   - 合并提交数量不变。
5. **带租约强推**：`git push --force-with-lease=main:<预期的旧提交> <地址> main`，
   远端如果被别人推过新内容就会拒绝，不会冲掉别人的提交。
6. 本地工作区切换：`git reset --soft <新提交>`（文件树相同，工作区与暂存内容不用动），
   再 `git fetch --all --prune` 刷新远端跟踪引用。其它机器上的克隆要么重新克隆，
   要么 `git fetch origin && git reset --hard origin/main`。

**最大的坑：退化合并会被默认剪掉。** 这次第一次改写后校验发现代码里少了「v0.9.1 代码审查修复」
那次提交的改动。原因是旧历史在这里是一个交叉合并：合并提交的第一父是只含凭据文件的提交，
第二父才是带代码修复的那条线。凭据提交变空被剪掉后，那次合并退化成「一个父提交是另一个的祖先」，
工具默认把退化合并也整个剪掉，第二父那条线的改动就从主线上丢了。
加 `--prune-degenerate never` 重做才对。**没有第 4 步的校验，这次就会把丢代码的历史强推上去。**

**清理历史不等于消除泄露。** 强推后实测：GitCode 与 Gitee 上旧的含私钥提交仍可匿名按编号拉取
（`git init && git fetch --depth 1 <地址> <旧提交编号>` 就能取到）。托管平台不会立刻清旧对象。
所以：密钥必须更换；要清掉平台上的旧对象得删除并重建仓库。

## 备份接收端的密钥限制要实测（2026-11-24）

沙箱往自有服务器推数据库备份，用的是服务器上带强制命令的受限公钥。实测结论：

| 写法 | 实际效果 |
|---|---|
| `rrsync -wo <目录>` | 只禁止读取。**仍然可以删除**——一次「带删除的同步」清空了备份目录 |
| `rrsync -wo -no-del -no-overwrite <目录>` | 只能新增：不能读、不能删、不能覆盖。配合 `restrict` 还不能端口转发、不能执行命令 |

所以受限公钥那一行必须写成：
`restrict,command="/usr/bin/rrsync -wo -no-del -no-overwrite <目录>" <公钥>`

**配好之后一定要用五项测试验证**（执行命令、读回、带删除同步、同名覆盖、端口转发），
并且要从管理通道核对服务器上的文件还在、哈希没变。没测过的限制等于没有。

另外三个坑：
- 目标路径必须写 `x@主机:.`，写 `/` 会被受限脚本判为不安全参数；
- 同步参数别用 `-a`，它会把本地目录的权限与属主套到服务器目录上（实测把目录从 700 改成了 775）；
  用 `-rlt --no-perms --no-owner --no-group`，脚本里设 `umask 077`；
- `server/backup_db.mjs` 默认找 `server/data/game.db`，线上库位置由环境变量指定时要带 `NH_DB=...`。

## 本机连不上服务器 22 端口时的排查顺序（2026-11-24）

现象：`kex_exchange_identification: Connection closed by remote host`，几小时前同样的密钥还能登录。

排查：
1. 先确认服务器本身是否正常——**换一条路径去连**，比如从 Instabox 沙箱里连：
   能到「Permission denied (publickey)」就说明 SSH 服务是通的，问题在本机这一侧；
2. 看本机路由：`route -n get <服务器地址>`。如果走的是 `utun` 网卡、网关是 `198.18.x.x`，
   就是代理软件的隧道模式在接管流量，出口节点到服务器这一段不通；
3. 不改任何代理设置的绕行办法：绑定物理网卡直连
   `ssh -b <本机局域网地址> x@<服务器真实地址>`。

注意读 22 端口欢迎信息的 `nc` 测试在这种网络下不可靠（连 github.com 都读不到），不能用它下结论。

## 重建仓库以清除平台上的旧对象（2026-11-24 实战）

上一节「清理历史不等于消除泄露」留下的问题，这一轮用重建仓库解决了：GitCode 与 Gitee 重建后，
含凭据的旧提交在四个远端都无法再按编号拉取。做法固定如下。

### 决定之前先查三件事

1. **有没有人复刻过**：`GET /api/v5/repos/{owner}/{repo}` 看 `forks_count`。只要不是 0，旧历史就留在
   别人的复刻里，重建主仓库没意义。
2. **会丢什么**：星标、议题、合并请求的数量。这次全是 0，所以代价为零。
3. **令牌够不够权限**：Gitee 的响应头里看不到权限范围，直接在临时仓库上演练最快。

### 顺序：先改名，不要先删

```
旧仓库改名 → 用原名新建 → 推送干净历史 → 改成公开 → 验证 → 删除改名后的旧仓库
```

先删后建的危险在于：新建一旦失败，原名就断了，所有克隆地址全部失效。
先改名的话，任何一步出问题都能把旧仓库改回原名，等于零风险。
脚本里每一步之后都检查结果，不符合预期就自动回滚（删掉新建的、把旧的改回去）并中止。

### 动真仓库之前在临时仓库上演练

用一个 `zz-` 开头的临时私有仓库把「新建、改名、同名再建、删除」走一遍，演练完立刻删除，
并再查一次确认没有残留（接口偶尔不返回结果，返回码是 `000`，要重查）。

### Gitee 接口的三个特点（都踩过）

| 现象 | 原因 | 处理 |
|---|---|---|
| 新建时不管怎么传参都是私有 | 接口只建得出私有空仓库 | 先接受私有，推送之后再改公开 |
| 改公开返回 422 | 「空仓库不支持设置为公开仓库」 | 必须先推送至少一个提交 |
| 改公开返回 400 `name is missing` | 修改仓库的接口**必须带 `name`** | `PATCH` 时带上 `name=<仓库名>&private=false` |

GitCode 的接口相反：新建出来直接是公开的，传 `private=true` 也不生效。

### 验证要带对照

「旧提交拉取被拒」本身不能证明对象没了——如果平台根本不支持按编号拉取，结果也是被拒。
所以要用一个**当前有效的提交编号**用同样方式拉一次作为对照：能拉到，才说明旧提交被拒是因为它确实不在了。

### 重建之后

- 仓库描述要单独恢复（新建时是空的）；
- 记下重建会改变仓库创建日期和内部编号；
- 托管平台的网页缓存可能还留一段时间旧文件的副本，管不到，靠更换密钥兜底。

## 把线上服务交给系统服务托管（2026-11-24）

原来 `/data/neon-heart/serve-loop.sh` 是用 `setsid nohup` 手动启动的，沙箱真正重启后不会自己回来。
现在交给 systemd 用户服务（单元文件在仓库 `deploy/instabox/`），运行行为不变，但多了开机自启，
而且守护脚本本身被杀也会被重新拉起。

切换时想让中断最短，顺序是：**先启动托管的实例，再停手动启动的旧实例**。
托管的实例发现端口被占会自己退出并每 2 秒重试，旧实例一停它就接管。停旧实例时先停守护脚本
（防止它再拉起服务进程），再停服务进程。

切换前确认了一件事：端口被占时服务进程记录一条错误后立即自行退出，不会僵持。
这一点之所以要确认，是因为之前加过「未捕获异常只记录不退出」的兜底，它有可能让进程卡在那里不退出，
那样重试机制就失效了。给服务进程加这类兜底之后，都要确认启动阶段的失败仍然是「会退出」的。

## 发布新版本到 Instabox 的步骤（v0.9.12 实战）

线上站点根目录是 `/data/neon-heart`（静态文件、`server/`、`data/` 数据库、守护脚本都在这里），
游戏服务由 systemd 用户服务 `neon-heart.service` 托管。实例编号用 `instabox ls --json` 查（名字会变，编号不变）。

1. **先提交并推送**，再 `npm run test:db:instabox -- all`——它测的是远端 main 的最新提交；
2. **部署前备份**：站点整目录打包（不含数据库）+ 跑一次 `backup.sh` 生成数据库快照；
3. **取代码**：`git clone --depth 1 https://gitcode.com/laotongtian/game1.git /data/home/game1-v09XX`，
   核对提交编号与 `VERSION`，确认没有凭据类文件；
4. **构建**：在克隆目录里 `node tools/build_bundle.mjs`；
5. **比对**：`diff -rq 克隆目录/server /data/neon-heart/server` 看服务端文件有没有变；
   再列出线上有、新产物没有的文件（应当只剩 `backup.sh`、`serve-loop.sh`、`VERSION` 这些要保留的）；
6. **替换**：`cp -a 克隆目录/dist/. /data/neon-heart/`；复制 `VERSION`；服务端有变化就复制变了的文件；
   数据目录与守护脚本不动；
7. **重启**：`systemctl --user restart neon-heart.service`，确认 `is-active` 为 active；
8. **沙箱内自检**：`/api/health` 的版本号、`/%` 返回 400、安全响应头、`bundle.js` 的哈希与本机构建一致；
9. **外部验收**（在本机）：`BASE=<线上地址>/index.html node tools/live-check.mjs` 看版本一致、代码包哈希一致、
   控制台错误 0；`curl -I` 看安全响应头；逐个请求敏感路径确认都是 404；
   `BASE=<线上地址> node tools/i18n-leak-scan.mjs --deep --selftest` 做线上英文模式实测。

**外部看到的才是真的**：沙箱内自检只说明服务起来了，响应头、缓存、代理层的问题只有从外部访问才看得到。

## 安全响应头（v0.9.12）

`server/index.mjs` 在请求入口一次性设置五个头，静态文件、接口、错误响应统一带上：
`X-Frame-Options: DENY`、`Content-Security-Policy: frame-ancestors 'none'`、`X-Content-Type-Options: nosniff`、
`Referrer-Policy: strict-origin-when-cross-origin`、`Permissions-Policy`（摄像头、麦克风、定位、支付、通用串行总线设备一律关闭）。

- **页面里原有的策略元标签不要删**：其余内容安全策略仍由它负责，纯静态部署（GitHub Pages、抱脸 Space）没有这个服务，只有它生效。
- **没有加强制安全传输（HSTS）**：它会把域名锁死为 HTTPS，而线上地址在 `instabox.tech` 的子域名上，
  一旦证书出问题用户会被锁在外面。要加需要用户确认。
- 改了 `server/` 下的代码，部署时**服务端文件也要替换**，不能只换静态文件。

## Instabox 命令行：密钥从指令文件里读，不要手敲（2026-11-25）

密钥有 56 个字符，手敲错一个字符的报错是 `invalid API key: no key has this secret`，
很容易被误判成「密钥被吊销了」。实际这次是打错了。

```bash
export INSTABOX_API_KEY=$(grep -o 'ibk_[a-z0-9]*' ~/.zcode/AGENTS.md | head -1)
```

登录态过期时报的是另一句 `session expired (unauthenticated)`，两者要分清。
