## 一、铁律：只发 dist

根目录有 68 个独立脚本，直接当站点根会串行请求，首屏 18.4 秒；
发 `dist/`（单 bundle）后约 3.5 秒。**任何平台都只发 dist。**

```bash
node tools/build_bundle.mjs
# 然后用 dist/ 的内容
```

## 三、自有服务器的历史坑

- **nginx 监听 9443**，因为 80/443 被服务器上既有的代理服务占用了，**不可触碰**
- **`add_header` 不继承**：在某个 `location` 里写了 `add_header`，
  父级的其他 `add_header` 会全部失效，必须在该层重写完整
- **`deploy.sh` 的清单必须与 index.html 的依赖一致**：
  早期漏了 `i18n/` 和 `privacy.html`，线上直接 404
- **`rsync --delete` 有风险**：源目录不全时会删掉线上文件
- 证书用 acme.sh 的 DNS-01 方式，自动续期

## 四、CDN 缓存滞后

GitHub Pages 改完 `gh-pages` 分支后，CDN 仍可能提供旧版本 10-15 分钟。
判断方法：直接看 `gh-pages` 分支内容是否已更新，
如果分支对了但线上还是旧的，就是 CDN 问题，不要反复改代码。

**用 bundle 哈希比对而不是只看页面能否打开。**

## 六、凭据管理

**含真实令牌的文档绝不能进仓库。** GitHub 有 Push Protection，
一旦推上去会被直接拦截（GH013），而且令牌已暴露在传输过程中。

正确做法：
1. 凭据文档写入 `.gitignore`
2. 需要给其它 AI 时，通过对话传递，不要靠仓库
3. 长期方案是模板 + 环境变量注入

当前的凭据文档：`docs/deploy-handoff-instabox.md`、`docs/deploy-handoff-prompt.md`，
两者都已在 `.gitignore` 里。

### 凭据必须实测验证，不能只靠抄

**血泪教训（2026-11-19）**：旧交接文档里的 SSH 私钥抄错了一个字符
（第 4 行 `dzAsK/3g` 应为 `dzAsp/3g`），base64 肉眼完全看不出来，
但密钥直接不可用。同批还发现 Hugging Face 令牌已返回 401 失效，
而文档里仍写着"可用"。

**写入凭据后的强制验证清单**：

```bash
# 1. Git 平台令牌：实际 ls-remote 一次
GIT_TERMINAL_PROMPT=0 git ls-remote https://用户名:令牌@域名/路径.git -h refs/heads/main

# 2. Instabox 密钥
INSTABOX_API_KEY=ibk_xxx instabox whoami

# 3. Hugging Face 令牌
curl -H "Authorization: Bearer hf_xxx" https://huggingface.co/api/whoami-v2

# 4. Cloudflare 令牌
curl -H "Authorization: Bearer cfut_xxx" https://api.cloudflare.com/client/v4/user/tokens/verify

# 5. SSH 私钥：能派生公钥就说明格式内容都对
ssh-keygen -y -f 提取出的私钥文件
diff 提取出的私钥 原始私钥文件      # 逐字节比对
```

每一条都要把**实测结果（可用 / 已失效）写进交付文档**。
写着"可用"但实际失效的凭据，会让接手的 AI 浪费大量时间排查，
比不提供凭据更糟。

## 七、GitHub Push Protection 的长期影响

GH013 拦截的是**整条历史**。即使后来把文件 `git rm --cached` 并从工作树删除，
只要历史提交里还有令牌，推送仍会被拒。

实测状态：GitHub main 停在 `b68ea33`，其它三个远端已到 `a417238`。
**代码本身无差异**（差的都是含凭据的文档提交），因此接受这个状态，
不做 force push 改写历史。

`gh-pages` 分支不含那些历史提交，**可以单独正常推送**。

## 八、gh-pages 分支容易被污染

实测发现该分支曾经有 **68MB**：包含 `node_modules`、`coverage`、`qa-shots`、
`test-results`、`.freebuff` 等开发垃圾，而且**缺少 `.nojekyll`**。

`gh-pages` 分支**只应该放 dist 的内容 + `.nojekyll` + `.gitignore`**。
缺 `.nojekyll` 会让 GitHub Pages 走 Jekyll 处理，下划线开头的资源可能 404。

更新方式是干净的 orphan 提交或直接把内容清空后复制 dist，不要增量叠加。

## 七、多远端一致性检查

当前可用的远端（AtomGit / GitCode / GitHub；本仓库当前未配置远端）：

```bash
for r in atomgit gitcode origin; do
  echo -n "$r: "; git ls-remote $r -h refs/heads/main | head -1
done
```

推送用 `bash push_all.sh`（纯 ASCII 输出，曾因多字节字符出过 `unbound variable`）。
**GitHub 因为令牌文档被拦，会比其它三个少几个纯文档提交，代码无差异，可接受。**

## 八、部署后必做验收

```bash
curl -s <地址>/index.html | grep -oE 'v0\.[0-9]+\.[0-9]+' | head -1
BASE=<地址>/index.html node tools/live-check.mjs
```

要求：版本一致、bundle 哈希一致、`errors: []`、`failed: []`。

## 九、可选账号服务的部署（v0.9.9）

账号服务与游戏同源，一个 Node 进程同时发静态和 `/api`，不需要 CORS：

```bash
cd /home/user/code/game1
server/ctl.sh start|stop|restart|status|logs
node server/backup_db.mjs        # VACUUM INTO 一致性备份
```

铁律：
- Node 必须是 **22+**（依赖内置 `node:sqlite`，不要 `npm install sqlite3`）
- `server/data/` 必须 gitignore：DB、WAL、日志、PID、备份都不能入库
- 静态服务必须把 `server/ docs/ tools/ 经验/ .git/ node_modules/` 等目录 404 掉
- HTTPS 终结在网关时，要把 `X-Forwarded-Proto` 传进来，否则 Cookie 不会带 `Secure`
- 公网部署时 `NH_SITE_ROOT` 指向 `dist`，但 `server/` 仍要在 Node 侧、不能进静态根

容器端口代理：本机 `8079` 的 `<port>-*` 反代按 Host 前缀取端口，
`curl -H 'Host: 8095-localhost:8079' http://127.0.0.1:8079/api/health` 可本地验证。

## Instabox：把静态站升级为 Node 同源服务（v0.9.9 实测）

- 沙箱自带 Node v22.23.3，`node:sqlite` 可用（有 ExperimentalWarning，不影响运行）。
- 纯 `python3 -m http.server` 只能发静态，账号卡片会显示“服务不可用”；
  换成 `server/index.mjs`（同端口发静态 + `/api`）后账号功能零改动可用。
- 启动三要素：`NH_PORT=9090`、`NH_SITE_ROOT=<站点根>`、`NH_DB=<仓库外路径>`。
- **必须把 `VERSION` 复制进站点根**，否则 `/api/health` 的 `version` 是 `unknown`。
- 停旧进程务必写 `pkill -f 'http.server 9090'`，同沙箱 8080 可能是别人的项目。
- 替换站点根用「先 `mv site site.old-时间戳` 再 `mv site.new site`」，失败可秒回滚。
