# 08 · 协作与流程

> 来源：多模型协作历史、用户直接在对话中下达的指令、禁提事项文档、push_all.sh 实践

## 一、用户最强调的一条：严禁提上架

**这是硬性禁令，违反会严重触怒用户。**

项目处于开发测试阶段，**绝不允许在任何分析、建议、总结、待办清单里
主动提及上架、发布、商店、分发平台、itch.io 等内容**。
只有用户自己先提起时才能讨论。

已写入 `docs/20261118-禁提事项-用户指令.md`。
这条优先级高于其它一切写作习惯（例如"给下一步建议时要全面"）。

## 二、多模型协作是常态

这个仓库先后由 GLM、DeepSeek、Doubao、Qoder、CodeArts、Seed、Qwen、M3、Kimi 等
多个模型改过。因此：

- 看到陌生提交时，**先怀疑是不是更早的自己或并行会话**，
  对照自己写过的计划文档，不要贸然断言"有别人在改"
- 提交信息里带版本号和模型署名，便于追溯
- 每个版本的问题记录写入 `docs/`，命名 `年月日-时分-标题-模型名.md`

## 三、文档规约

1. 文档统一命名 `YYYYMMDD-HHMM-<标题>-<模型名>.md`
2. **写了文档就必须同步更新根目录 `文档索引.md`**，否则等于没写
3. README 只放【当前开发进度】【下一步待实现】摘要，详细内容进 docs，
   README 要指向对应的两个 docs 文件
4. 根目录 `经验/` 存放从 docs 提炼出的做法手册（docs 不一定对，经验要准）

## 四、Git 远端

项目根 `push_all.sh` 会遍历当前已配置的全部远端并检查 HEAD 是否一致。
本仓库当前未配置远端；需要推送时由用户指定目标，AtomGit 等平台单独处理。

```bash
for r in $(git remote); do
  echo -n "$r: "; git ls-remote $r -h refs/heads/main | head -1
done
```

**注意**：
- 不要 force push main
- 提交信息用中文
- `push_all.sh` 必须是纯 ASCII 输出，曾因多字节字符导致 `unbound variable`
- **含真实令牌的文件绝不能提交**，GitHub 会拦截（GH013）并暴露令牌

## 五、版本号规矩

每次改源代码就把版本号加 0.0.1。用脚本改：

```bash
python3 tools/bump_version.py 0.9.7
node check_version.js
```

## 六、修改完成的标准

**不允许"改完就停"**。每轮必须：

```bash
npm run test:all        # 全绿
node tools/build_bundle.mjs
```

线上部署的还要跑 `node tools/live-check.mjs`。
失败就继续修，不能带着失败停下。

## 七、发现可优化点时主动说

用户明确要求：发现能明显提升、优化的方向时**主动告知详情**，
特别是与已有要求冲突时，交给用户决定是否优化。

但注意与第一条的边界：主动建议里**不能碰发布相关内容**。

## 八、代码风格

- 注释用中文
- 回复用详细中文，不用简称
- 英文专有名词后面附中文
- 代码要读起来像周围的代码（命名、注释密度、惯用法保持一致）

## 九、本机操作注意事项

- 运行 Python 程序前先检查项目内虚拟环境，没有就创建并激活
- 不在本机装 MySQL 等，需要数据库就启 Docker
- 做界面操作优先用 computer-use 技能，不要前台点击影响用户使用电脑
- 本机是 M5 / macOS 27，与服务器环境严格区分

## 九、多会话共享容器的并发冲突（v0.9.9 实测）

**事实**：容器文件层跨会话共享——`/home/user` 是持久卷，项目目录 `/home/user/code/game1`
是**同一份 git 工作区**。每个会话只有独立的进程与系统层，文件与 git 索引是共用的。

**症状**：开工时 `git status` 出现大量自己没改过的文件、mtime 在几分钟内、别的
`system/trajectory.jsonl` 仍在增长——说明另一个会话正在同一目录写代码。

**本轮实例**：一个会话（CodeArts）已实现服务端账号系统（`server/` 四表 + `ui/25_account.js`
759 行）并 commit；另一个会话（豆包）同时写了本地版 `account.js` / `cloud-sync.js` /
`server/account-server.mjs`。发现后立刻删除自己新建的未跟踪文件，未污染对方提交。

**正确处置顺序**：

1. `git log --oneline -3` + `git status --short` + `ls --time-style=full-iso` 看文件 mtime；
2. 查其它会话 trajectory 是否仍在更新（判断对方是否活跃）；
3. **绝不覆盖对方已存在的文件**；自己新建的未跟踪文件在确认冲突后立即撤出；
4. 等对方 commit 完成、工作区干净后，再接手验证 / 推送 / 文档；
5. 若必须并行，另开独立 clone（`git clone` 到别的目录），不要共用工作区。

**禁止**：两个会话同时 Edit 同一文件；一个会话 `git add -A` 会把对方半成品一起提交；
在对方运行测试时抢占同一端口 / SQLite 文件。

## 十、每次拉取都要对比所有远端的头（2026-11-24 教训）

GitHub 上有一条 11 月 20 日提交的修复，**四天里没有任何人发现它没被并回主线**。
主线缺着它里面的修复，同一个缺陷后来被另一个 AI 又修了一遍。

原因：大家都只从 GitCode 拉、往 GitCode 推；GitHub 因为推送保护一直推不上去，
于是它的头停在旧基线上，另一个 AI 在它上面单独开发了一条线。

**每次拉取后必须做的一步**：

```bash
git fetch --all
for r in gitcode atomgit gitee origin; do echo -n "$r: "; git rev-parse --short $r/main; done
git log --oneline HEAD..origin/main        # 有输出 = 有没并回来的提交
```

发现分叉时：先看双方各自改了什么（`git diff --stat A B`），逐文件决定取舍，
用合并提交并回去（`git merge --no-commit` 后逐个处理冲突），**不要选一边丢掉另一边**。

远端事实：AtomGit 与 GitCode 是同一个仓库的两个域名，推 GitCode 即等于推 AtomGit
（AtomGit 本地保存的凭据已失效，推送会报认证失败，但实际已经更新）。
GitHub 在历史里的凭据清理之前推不上去，属于已知状态。

## 十一、合并提交要保持干净

把「合并」和「修复」分成两个提交，后来的人才能看懂。
做法：合并产生冲突并解决后，暂存区里就是纯合并结果；这时不要在里面混入新改动。
如果已经混在一起了，可以从暂存区单独生成合并提交：

```bash
TREE=$(git write-tree)
M=$(git commit-tree $TREE -p HEAD -p <对方的提交> -F 合并说明.txt)
rm -f .git/MERGE_HEAD .git/MERGE_MSG .git/MERGE_MODE .git/AUTO_MERGE   # 清掉「合并进行中」标记
git reset --soft $M          # 分支移到合并提交，工作区与暂存内容不动
git add -A && git commit -F 修复说明.txt   # 修复作为下一个提交
```

## 十二、分析结论要先验证再写

- 写进报告的每个数字都要能复现；是估算的就标明是估算，或者干脆去实测。
  2026-11-24 有一处「估算收敛到 80% 以上」，实测后发现完全不对，重写成了真实数据。
- 分析脚本本身可能有错（见 `经验/05` 第十节）。第一版报告的触达率与「不可达事件数」都错过一次，
  靠通读复核发现。**报告写完后要带着「哪里可能算错了」的心态再读一遍。**
- 「修复前」的数据要用修复前的代码实测，不要引用记忆或旧日志。

## 十三、历史改写之后的协作规矩（2026-11-24）

北京时间 2026-11-24 03:50 前后，仓库历史被整体改写（清除历史里的凭据），**此后所有提交编号都变了**。

- 改写之前克隆的仓库：重新克隆，或 `git fetch origin && git reset --hard origin/main`；
- **不要从旧克隆里强推或合并**，否则会把带凭据的历史重新带回来；
- 旧文档里引用的提交编号是改写前的，对照表见 `docs/20261124-0446-Git历史清理与线上部署与备份建立-GLM-5.4.md`；
- 旧历史的备份在仓库之外，含旧凭据，密钥更换完成后删除。

改写历史这种操作要同时满足三件事才做：用户明确同意、已备份、改写后逐提交校验。
校验不通过就重做，不要带着疑点强推。

## 十四、线上可能运行着仓库里没有的代码

2026-11-24 部署前发现线上站点目录里多了一个仓库中没有的翻译文件。排查方法：

1. 把线上代码包和本地构建都按分隔标记 `/* ===== 文件名 ===== */` 拆开，逐文件对比；
2. 确认多出来的文件有没有被首页引用、有没有进代码包和离线缓存——没被加载的就是孤立文件，不影响运行；
3. 结论要以「线上代码与仓库逐文件一致 / 不一致」为准，再决定能不能直接覆盖。

这次的结果是逐文件一致，可以放心覆盖；孤立文件原样保留。如果没有先做这一步，
要么误以为线上有另一套代码而不敢部署，要么把别人未推送的工作直接抹掉。

## 十五、本机不跑数据库（2026-11-24 用户规则）

用户更新了全局规则：**本机不启动数据库、不启动 Docker、不部署任何环境（包括临时实验用的容器）；
需要数据库或真实运行环境时一律放到 Instabox；本机只做读改代码、Git 操作、不依赖数据库的单测与静态检查。**

这条规则直接改变了我前一天建的总闸：当时「账号接口测试」被放在每次推送都跑的集合里，
而它会启动服务进程并用 SQLite。发现冲突后已调整，详见 `经验/05` 第十三节。

**做法上的提醒**：用户的规则文件每次会话开始都会重新读取，内容可能变了。
自己之前建的自动化（钩子、总闸、脚本）要对照新规则复查一遍，不要默认它们还合规。

## 十六、用户说「你决定」时怎么做

2026-11-24 用户把两件事交给我决定：是否重建仓库、是否给服务加开机自启。做法是：

1. **先查事实再决定**。重建仓库之前先查有没有复刻、会丢什么、令牌够不够权限。
   如果当时查出有复刻，结论就会是不重建。
2. **先演练，再动真的**。在临时仓库上把整套流程走通，演练完清理干净并复查。
3. **带回滚地执行**。真仓库的操作脚本每一步都检查，不符合预期就自动恢复原状。
   这次 Gitee 第一次执行真的触发了回滚，没有造成任何损失。
4. **验证要带对照**，否则「被拒」可能只是接口不支持。
5. 做不到或验证不了的事要照实说（例如沙箱重启后自动恢复没有实测机会）。

依然不替用户做的事：更换密钥。那会改用户自己的登录方式和各种工具的配置，
而且有查不清的依赖（比如服务器上的证书续期可能正用着同一个 Cloudflare 令牌）。
