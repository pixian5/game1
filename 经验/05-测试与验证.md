# 05 · 测试与验证

> 来源：v0.1.4 测试基建、v0.7.0 测试稳定性根修、v0.7.6 测试修复复验、v0.8.7 商业级测试

## 一、四层测试结构

```bash
npm run check:version      # 版本号五处一致性
npm run validate:story     # 剧情数据合法性（338 事件 / 18 临界 / 17 结局 / 19 收集）
npm run check:ui           # UI 层静态校验
npm run lint               # eslint
npm run test:regressions   # 回归（历史 bug 的守护用例）
npm run test:story         # 剧情链路 294 条断言，假时钟，约 0.13 秒
npm run test:browser       # Playwright 三浏览器 E2E

npm run test:all           # 以上全部串联
```

**顺序有意义**：越靠前的越快、越便宜，失败时定位越准。

## 二、假时钟是提速关键

`tools/fake_clock.js` 提供虚拟时钟，把原本要等真实时间流逝的剧情链
压缩到 0.13 秒跑完 294 条断言。没有它，剧情测试根本跑不动。

**使用注意**：假时钟接管了定时器，
用例里如果自己替换了 `sandbox.localStorage.setItem` 或实例的 `_setTimeout`，
**必须用 `try/finally` 还原**，否则会污染后续用例。

**这个坑造成的假象**：`test_story` 曾出现间歇性失败，
一度被误判为代码回归，实际是前面某个用例没还原定时器。
现在改成增量断言（先记录基线，再比较差值）就稳定了。

## 三、浏览器矩阵

`playwright.config.js` 有三个 project：chromium / firefox / webkit，
统一指向 `http://127.0.0.1:4187`（由 `test_server.js` 提供）。

**一律用 `npm run test:browser` 跑**（v0.9.12 起 75 项）。它自带排除账号用例的参数；
直接调用 `playwright test` 会把账号端到端带进来，在本机启动带临时数据库的服务（见第十三节）。

chromium 这一档默认用 **Playwright 自带的内核**（`PW_CHANNEL` 默认为 `none`，2026-11-25 改），
需要时用环境变量换：

```bash
PW_CHANNEL=chrome npm run test:browser       # 用电脑上真实安装的谷歌浏览器
PW_EXECUTABLE_PATH=/path/to/chrome npm run test:browser
```

改默认的原因（实测）：真实安装的谷歌浏览器（158 版）在**两个工作进程同时收尾**时会卡死不退出，
要等 300 秒被强制结束，整组用例被判失败——而 75 项其实全部通过。
上一版代码 49 秒正常，单独跑任何一个内核都正常，只有「真实浏览器 + 两个进程并行」才卡。
之前没暴露只是各进程结束时间刚好错开；新加的用例各跑 10 秒，两个进程恰好同时结束，才稳定撞上。
排查这类问题的办法：先看失败输出里「通过数」与「进程未退出」是不是同时出现，再拿上一版代码、
单内核、单进程（`--workers=1`）分别做对照，不要先怀疑自己的页面代码。

**三浏览器全绿才算过**。历史上出现过只在 webkit 挂的问题（图片解码时机）。

## 四、图片加载的假阳性

E2E 里断言头像尺寸时曾经拿到 `naturalWidth: 0`，
原因是图片有 `loading="lazy"`，还没解码。

**正确写法**：不要同步读属性，要等待条件成立。

```js
await page.waitForFunction(() => {
  const img = document.querySelector('...');
  return img && img.complete && img.naturalWidth === 128;
});
```

类似地，任何依赖网络/解码的断言都要用 `waitForFunction` 或 `waitForSelector`，
不要用固定的 `setTimeout` 等待。

## 七、线上验收标准

```bash
BASE=https://某地址/index.html node tools/live-check.mjs
```

必须同时满足：
- `versionMatch: true`（线上版本 == 本地 VERSION）
- `bundle.match: true`（线上 bundle 哈希 == 本地构建哈希）
- `errors: []`
- `failed: []`

**只看到"能打开"不算通过。** 曾经多次出现"页面能开但版本是旧的"，
靠 bundle 哈希比对才能发现。

## 八、测试必须模拟「慢玩家」（v0.9.11 的最大教训）

**所有自动作答的脚本都会漏掉同一类缺陷。** 之前全流程脚本、路线矩阵、剧情链路测试
都是「一看到选择就立刻回复」，所以从来没有两个选择同时挂着，
「后到的选择顶掉先到的」这个缺陷在所有测试全绿的情况下存在了好几个版本。

真实玩家会先去干别的，几小时后才回来回复。所以要有一种测试专门这样做：

```bash
node tools/choice_override_probe.mjs                  # 默认延迟 0 / 2 / 6 / 12 游戏小时
node tools/choice_override_probe.mjs --delays 0,2,6,12,24
```

它做了什么：
- 用**事件驱动**的方式驱动真实剧情：真实时间每步前进 1 秒，让打字延迟、消息投递、
  后续事件派发自然发生；全屏强制交互出现就处理；玩家空闲时「出行」推进 30 分钟游戏时间。
  **不要手动改写 `state.day`**——主线靠剧情里的 `advance_day` 事件自己推进日期，
  手动改日期会把主线搅乱，得到「0 次覆盖」的假结果（2026-11-24 踩过）。
- 接管 `Date.now()` 跟随虚拟时钟。邀约超时（120 秒）、来电未接（25 秒）用的是真实墙上时间，
  不接管的话邀约在模拟里永远不会超时。
- 判断「当前选择换了人」时分两种：旧选择仍在队列里是设计行为（邀约让位），不计；
  旧选择既不是当前选择也不在队列里才是静默丢失。
- 出现任何静默丢失、或任何一条路线没走到结局 → 退出码 1。已挂进 `test:all` 与 `verify:offline`。

其它可调参数：`--routes shenyan,luci`、`--finale-gate=12`（结局门槛）、`--max-day=40`、`--json`（结构化输出）。

## 九、修复前的数据怎么量

要报告「修复前是什么样」，不能靠记忆或旧日志。把修复前的提交检出到临时目录再量一次：

```bash
git worktree add --detach /tmp/game1-prefix <修复前的提交>
cp tools/choice_override_probe.mjs /tmp/game1-prefix/tools/
cd /tmp/game1-prefix && node tools/choice_override_probe.mjs --delays 0,2,6,12,24
cd - && git worktree remove --force /tmp/game1-prefix && git worktree prune
```

这样修复前后用的是同一个工具、同一组参数，数字才可比。

## 十、分析脚本本身要先验证

写脚本统计「多少事件可达」时，脚本里对触发条件的理解必须和引擎一致。
2026-11-24 的教训：分析脚本把 `inRoute` 当成路线编号去比较，
而它在剧情里的值是布尔值 `true`（表示「在任意一条男主线内可见」），
结果 7 条事件被误判成永远不可见，第一版报告的触达率和「不可达事件数」都是错的，
通读复核时才发现。

**做法**：分析脚本写完先列一遍数据里实际用到的字段和取值（`trigger` 一共只有六个字段），
对照 `engine.js` 里的判断逐个确认，再用一两个已知会触发的事件做对照。

## 十二、总闸与推送前钩子（2026-11-24 建立）

上面第十一节的问题（21 个脚本没接进流程）已处理。现在的用法：

| 命令 | 在哪里跑 | 内容 | 用时 |
|---|---|---|---|
| 推送前钩子（自动） | 本机 | `verify:offline`（含翻译层测试、两项文字覆盖检查）+ 代码规范 | 约 47 秒 |
| `npm run gate` | 本机 | 上一行 + 结局可达性、翻译缺口、安全、离线可用性、英文模式首层实测 | 约 90 秒 |
| `npm run gate:full` | 本机 | 上一行 + 三浏览器端到端 + 英文模式深入实测 | 约 4.2 分钟 |
| `npm run test:db:instabox` | **Instabox** | 账号接口测试 74 项 | 约 15 秒 |
| `npm run test:db:instabox -- all` | **Instabox** | 上一行 + 账号与云存档端到端 | 约 30 秒 |

- **依赖数据库的测试不在本机跑**（见第十三节）。
- 实现在 `tools/run_gate.mjs`。四项浏览器检查需要本地服务器，脚本会代为启动并在结束后关闭。
- 同一提交通过后记标记 `.gate-stamp`（不入库），往多个远端连续推送不重复跑。
  工作区有未提交改动时不记标记（检查的是工作区，不是提交本身）。
- 钩子在 `.githooks/pre-push`，`npm install` 时由 `prepare` 脚本自动启用。跳过某一次：`SKIP_GATE=1`。

**改动钩子脚本之后必须先做 `sh -n`。** 第一版钩子里把 `fi` 写成了 `}`，语法检查直接拦住——
这种错误一旦启用，所有推送都会失败，而且是别人的会话先发现。

**钩子的三条路径都要验证**：跳过路径（`SKIP_GATE=1`）、通过路径（喂一行待推送引用给脚本）、
**拦截路径**（故意把 `VERSION` 改坏，确认钩子返回 1，再还原）。只验证通过路径等于没验证。

现有的 `check:i18n` 只报「字典里有没有这个键」，结果是 0 条缺口，但英文模式下选项仍然是中文——
翻译有了而界面没用，它扫不到。这类「字典覆盖率」指标不等于「界面上没有中文」。
v0.9.12 起由三样东西兜底：`check:i18n-literals`（扫源码）、`check:i18n-leak`（浏览器实测）、
端到端里的「英文模式下全部应用不显示中文」。做法见 `经验/03-双语与i18n.md`。

## 十三、依赖数据库的测试一律放到 Instabox（2026-11-24 用户规则）

用户的规定：**本机不启动数据库、不启动 Docker、不部署任何环境；需要数据库或真实运行环境时一律放到
Instabox；本机只做读改代码、Git 操作、不依赖数据库的单测与静态检查。**

按这条规定，下面两个测试不能在本机跑——它们都会启动账号服务进程并用 SQLite：
`server/test_api.mjs`（账号接口测试）和 `playwright/account.spec.js`（账号与云存档端到端）。

做法：

- `verify:offline` 里不再包含账号接口测试，所以本机的钩子和总闸都不碰数据库；
- 新增 `npm run test:db:instabox`（`tools/instabox_db_tests.sh`）：把 `deploy/instabox/run-db-tests.sh`
  推到沙箱，在沙箱里重新克隆 main 并执行。默认只跑接口测试，加 `-- all` 再跑账号端到端；
- `npm run test:all` 仍然包含数据库测试，只适合在允许跑数据库的环境里用；
- 密钥不写在仓库脚本里（仓库是公开的），靠 `instabox login` 或环境变量 `INSTABOX_API_KEY`。

沙箱里的实测条件：有 Node 与 `node:sqlite`，有系统自带的 Google Chrome，`npm install` 能装上测试依赖
（只装在那个克隆目录里）。账号接口 74 项、账号端到端 1 项都通过。

**2026-11-25 自己踩过一次**：排查端到端卡死时直接调用 `playwright test` 做对照实验，两次都漏了排除参数，
在本机短暂启动了带临时数据库的服务。虽无残留，但违反规定。做对照实验也要用项目自带的命令。

**注意 `instabox` 命令行工具的登录态会过期**（报 `session expired (unauthenticated)`）。
本机入口脚本遇到这种情况会给出明确提示，而不是只打印一行原始报错。

改了 `server/` 下的代码后，收尾时要执行的是两件事：本机 `npm run gate`，加上 `npm run test:db:instabox -- all`。

## 十四、「零残留」类检查必须自证（2026-11-25 的教训）

统计「还有多少问题」的检查，最危险的失败方式不是报错，而是**报 0**。

当天连续遇到三次：

1. 扫描脚本里对空结果调用了 `.length`，干净的界面全被算成「出错」，真正的残留反而没显示；
2. 页面里 `page.evaluate` 内的变量不会自己传出来，结果数组永远是空的；
3. **等待函数写错成「不等待」**：扫描在界面还没渲染完时就取文字，31 个应用全报有残留，
   而点击 260 次、看到 111 条文字这些统计数字看着都合理——这一次是反方向：报了一堆假问题。

所以 `tools/i18n-leak-scan.mjs` 现在自带三道自证，缺一个都不算数：

- **对照自检**：扫描前故意往页面里放两条中文（手机容器外、内各一条），结束时必须都被抓到；
- **等待函数硬性自检**：先实测等 200 毫秒，实际不足 150 毫秒就抛错，不让结果流出去；
- **结果不可信就退出码 2**：没打开任何应用、没看到界面文字、页面抛出异常、自检失败。
  退出码 2 与「有残留」的 1 分开，调用方不会把「工具坏了」当成「没有问题」。

这套自证本身也做了**反向对照**：故意把等待函数改坏，确认工具报错退出而不是输出结果。

**通用的做法**：凡是输出「0 个问题」的检查，都要 (1) 打印「扫描范围」的统计（打开了几个、看到了几条）；
(2) 内置一个必然会被抓到的样本；(3) 对关键检查做一次反向对照——故意弄坏一处，确认它会报错。
只验证通过路径等于没验证。
