## 二、决定重建仓库的依据

动手前先查清事实，而不是直接删：

| 事实 | Gitee | GitCode |
|---|---|---|
| 被别人复刻的数量 | 0 | 0 |
| 星标 / 议题 | 0 / 0 | 0 / 0 |
| 令牌权限 | 能新建、改名、删除 | 全部权限 |

**复刻数是 0 这一点最关键**：如果有人复刻过，旧历史会留在复刻里，删主仓库也清不掉。既然没有复刻、也没有任何会丢的星标和议题，重建的代价几乎为零，而收益是把平台上的旧凭据对象真正清掉。所以决定重建。

**不采用「先删后建」**：那样一旦新建失败，原名就断了。改用更安全的顺序，任何一步不符合预期都自动把旧仓库改回原名：

```
旧仓库改名  →  用原名新建  →  推送干净历史  →  改成公开  →  验证  →  删除改名后的旧仓库
```

动真仓库之前，先在临时私有仓库上把整套流程（新建、改名、同名再建、删除）演练通过，临时仓库随即删除，无残留。

## 三、Gitee：第一次执行被自己的保护逻辑拦下

第一次对真实仓库执行时，脚本在「新建」这一步**自动中止并回滚**：接口建出来的是私有仓库，不符合「必须是公开仓库」的预期。

- 回滚动作：删掉刚建的那个私有空仓库，把旧仓库改回原名。
- 回滚后核实：`ibjxk/leame` 仍是原来那个仓库（创建日期还是 8 月 5 日，分支头没变），没有任何损失。

排查原因（都在临时仓库上做）：

| 尝试 | 结果 |
|---|---|
| 新建时传 `private=false`、`private=0`、不传、用 JSON 体 | 一律建成私有 |
| 建完后用接口改成公开 | 返回 422，说明是：**「空仓库不支持设置为公开仓库」** |
| 先推送一个提交，再改成公开 | 成功 |

所以正确顺序是「新建 → 推送 → 再改公开」。把这一步补进脚本后第二次执行成功：

```
改名 200 → 新建 201（私有）→ 推送成功，分支头 bf9a06f → 改公开成功 → 默认分支 main → 删除旧仓库 204
```

排查过程中我的试验脚本自身出过两个小错（字符串格式错误导致中途崩溃、留下一个临时私有仓库），都已发现并清理干净，账号下没有 `zz-` 开头的临时仓库残留。

## 六、游戏服务改成开机自启

**决定：做。** 此前守护脚本是手动拉起的，沙箱真正重启后服务不会自己恢复。

做法：新增 systemd 用户服务单元托管现有的守护脚本（运行行为不变），设为开机自启。

切换顺序（为了把中断压到最短）：

1. 先启动托管的实例——它发现端口被占会每 2 秒重试一次；
2. 再停掉手动启动的旧实例（先停守护脚本，防止它再拉起进程；再停服务进程）；
3. 托管实例在下一个重试周期接管。

切换前专门实测了一个风险点：我上一轮给服务加过「未捕获异常只记录不退出」的兜底，担心端口被占时进程会僵着不退出、导致重试机制失效。实测结果是进程记录一条错误后**立即自行退出**，不会僵持。

| 验证项 | 结果 |
|---|---|
| 守护脚本的上级进程 | 用户级服务管理器（确认已归 systemd 托管） |
| 服务进程被强制杀掉 | 约 2 秒后恢复 |
| 守护脚本本身被强制杀掉 | 约 4 秒后恢复 |
| 开机自启 | 已启用 |
| 外部验收 | 版本一致、代码包哈希一致、控制台错误 0 |

**没能实测的一点**：沙箱「真正重启后自动恢复」本身。不想为了验证而重启正在服务的沙箱。依据是标准机制（开机时用户级服务管理器启动默认目标，默认目标包含这个已启用的服务）。详见 [deploy/instabox/README.md](../deploy/instabox/README.md)。

## 七、依赖数据库的测试分流到 Instabox

用户更新了全局规则：**本机不启动数据库、不部署任何环境；需要数据库或真实运行环境时一律放到 Instabox；本机只做读改代码、Git 操作、不依赖数据库的单测与静态检查。**

我上一轮建的总闸和推送前钩子里包含「账号接口测试」——它会启动服务进程并使用 SQLite 数据库，并且每次推送都会在本机跑。这与新规则冲突，调整如下：

| 命令 | 在哪里跑 | 内容 |
|---|---|---|
| 推送前钩子（自动） | 本机 | 离线检查集 + 代码规范，不含任何数据库测试，约 47 秒 |
| `npm run gate` / `gate:full` | 本机 | 上一行 + 四项浏览器检查（+/ 三浏览器端到端），都不依赖数据库 |
| `npm run test:db:instabox` | **Instabox** | 账号接口测试（54 项，约 15 秒） |
| `npm run test:db:instabox -- all` | **Instabox** | 上一行 + 账号与云存档浏览器端到端（约 1 分钟） |

沙箱上的实测：账号接口 54 项全过；账号端到端 1 项通过。
`npm run test:all` 仍然包含数据库测试，只适合在允许跑数据库的环境（如 Instabox）里用。

密钥不写在仓库里的脚本中（本仓库是公开的），脚本依赖 `instabox login` 或环境变量 `INSTABOX_API_KEY`，未认证时会给出明确提示。
