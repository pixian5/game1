## 二、清理 Git 历史

### 2.1 泄露范围（比上一轮报告的更大）

逐个扫描全部 198 个历史提交后确认，含凭据的是两份文档：

| `docs/deploy-handoff-prompt.md` | 服务器 SSH 私钥、GitHub 令牌、抱脸令牌、Cloudflare 令牌、Gitee 令牌、GitCode 令牌、推送密钥 | 1 个提交 | 文件本身早已删除，但历史里还在 |

### 2.2 做法

1. **先备份**：旧历史完整打包到仓库之外（`~/.game1-backups/game1-history-before-cleanup-20261124.bundle`，198 个提交，已校验完整，权限仅本人可读）。**这个备份本身含旧凭据**，密钥更换完成后可以删除。
2. **在全新克隆里改写**，不动工作区：
   - 整份交接文件从全部历史里移除；
   - 所有已知令牌字面量在全部历史里替换为占位符（双保险）；
   - 参数 `--prune-degenerate never`，保留退化合并（原因见 2.4）。
3. **强推前逐提交校验**（见 2.3）。
4. **带租约强推**：只有远端仍是预期旧提交时才覆盖，避免冲掉别人在这期间推的内容。
5. 本地工作区与沙箱上的三个代码克隆切换到新历史，旧对象清理掉。

### 2.4 第一次改写是错的（靠校验拦住）

第一次改写后校验发现：文件树不一致，新代码里**少了**「v0.9.1 代码审查修复」那次提交的改动和一份文档。

原因：旧历史在这里是一个交叉合并——合并提交的**第一父**是只含凭据文件的提交，**第二父**才是带代码修复的那条线。凭据提交变空被剪掉后，那次合并退化成「一个父提交是另一个的祖先」，工具默认把退化合并也整个剪掉，于是第二父那条线的改动从主线上丢了。

处理：加 `--prune-degenerate never` 重做，再次逐提交核对通过后才推送。

**教训：改写历史必须先备份、改写后必须逐提交核对内容，确认无误再强推。**

### 2.5 清理之后的事实：平台上的旧对象还在

分支指向新历史后，我用不带凭据的方式按旧提交编号直接拉取：

| 平台 | 旧的含私钥提交是否仍可获取 |
|---|---|
| GitHub | 否（它从未有过这个提交） |
| GitCode | **是**，匿名可拉取，文件内私钥标记仍在 |
| Gitee | **是**，网页地址可直接下载 |

强推只改变分支指向，托管平台不会立即清除旧对象。因此：

1. **更换密钥是必须的**，清理历史代替不了。泄露的内容（SSH 私钥、各平台令牌）都是可以更换的，换掉之后旧提交即使还能拉到也无害。
2. 要彻底清掉平台上的旧对象，需要**删除并重建 GitCode 与 Gitee 上的仓库**（新仓库不含旧对象，地址不变）。这一步破坏性大，本轮没有做，留给用户确认。

另外核实了一件事：2026-10-29 的文档记录「GitCode 仓库匿名可推送」。本轮实测 GitCode 与 Gitee **都已拒绝**不带凭据的推送，该问题已不存在。

### 2.6 对其它会话的影响

**北京时间 2026-11-24 03:50 前后（旧历史备份生成于 03:48，随后完成强推），所有提交编号都变了。** 旧的克隆必须重新克隆，或执行：

## 四、数据库备份

详见 [deploy/backup/README.md](../deploy/backup/README.md)。要点：

| 项目 | 实测结果 |
|---|---|
| 链路 | 快照 → 完整性校验 → 本地保留 14 份 → 推送到 `uw`、`ue` 各一份；首次运行成功 |
| 文件对账 | 沙箱原件与两台服务器上的文件哈希一致（`a67ceb1ab12fe950…`） |
| 调度 | systemd 用户定时器，每天 UTC 03:30（北京时间 11:30），错过后补跑 |
| 权限限制 | 执行命令、读回、删除、覆盖、端口转发五项全部被拒 |
| 恢复演练 | 从服务器取回备份 → 临时实例加载 → 在恢复的库上完成注册与登录，全部成功 |

**实测踩到并已修正的问题**：

1. 受限同步脚本的「只写」模式**并不禁止删除**。只加 `-wo` 时，一次「带删除的同步」清空了 `uw` 上的备份目录（当时只有两个空库测试备份，重跑即恢复）。已加 `-no-del -no-overwrite`，并把删除与覆盖两项纳入实测。
2. 同步参数用 `-a` 会把本地目录的权限套到服务器目录上（从「仅本人可读写」变成「组内可写」）。已改用 `-rlt --no-perms --no-owner --no-group`。
3. 目标路径写成 `/` 会被受限脚本判为不安全参数，必须写 `.`。
4. 备份脚本默认找另一个路径的数据库，需要带上 `NH_DB`。
5. 本机到服务器 22 端口一度连不上，是本机代理隧道出口到服务器这一段不通；服务器本身正常。绑定物理网卡直连即可，未改动任何代理设置。

**已知限制**：沙箱暂停期间定时器不运行（恢复后补跑）；备份未做静态加密；服务器登录密钥尚未更换；游戏服务进程没有开机自启。

## 五、自动化检查（自行决定并已实施）

- 新增总闸 `tools/run_gate.mjs`，三档：
  - 离线档（推送前钩子用）：`verify:offline` + 代码规范，约 48 秒，不依赖浏览器；
  - 默认档 `npm run gate`：加结局可达性、翻译缺口、安全、离线可用性，约 76 秒；
  - 完整档 `npm run gate:full`：再加账号端到端与三浏览器端到端。
- 同一提交通过后记标记（`.gate-stamp`，不入库），往多个远端连续推送不重复跑。
- 推送前钩子 `.githooks/pre-push`，`npm install` 时自动启用；检查失败则中止推送。
- 新增 npm 命令：`gate`、`gate:full`、`check:endings`、`check:i18n`、`check:security`、`check:pwa`。

实测：默认档 6 步全过；钩子的跳过路径、通过路径、**拦截路径**（故意把版本号改坏，钩子返回 1）都验证过。

钩子第一版有一处语法错误（把 `fi` 写成了 `}`），被 `sh -n` 语法检查拦住——这种错误一旦启用会让所有推送都失败。钩子脚本改动后务必先跑 `sh -n`。

## 六、其余三项自行决定的事项

### 6.1 剧情保底长度：目标 12 天，但不打开原型开关

实测打开原型开关（`STORY.finaleGate = 12`）后：回归、路线矩阵、覆盖探测都通过，但**剧情链路测试有 8 项失败**。

失败暴露的不只是测试问题：这个原型的语义是「路线主线从第 12 天才开始」，而游戏里的日期很大程度靠主线自己的「次日」事件推进。结果是玩家在 day6–7 选完线，要靠反复出行干等 5 天才进入主线，day10 一天只有 2 条带日期事件。这是节奏上的倒退。

**决定**：下一版按「路线主线照常开始，只把最终结局压到第 12 天之后」的方式实施，并补过渡内容、处理 10 条永远触达不到的事件，作为单独一个版本认真做，不草率打开开关。

### 6.2 自有服务器对外方式：定 Cloudflare Tunnel，实施排在密钥更换之后

两台服务器的 80/443/2053/2083/8443 都被既有代理服务占用，隧道方案不需要开放入站端口，最合适。

但两台服务器的登录私钥已泄露，Cloudflare 令牌也已泄露。在更换之前把带用户数据的账号服务部署上去不合适。所以本轮只把两台服务器用作备份接收端（当前库内没有真实用户），对外部署留到密钥更换之后。
