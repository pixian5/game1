## 二、为什么要从 python 静态服务换成 Node

账号前端默认**同源**请求 `/api/*`（`meta[name="neon-account-api"]` 留空）。纯静态托管下
账号卡片只能显示“账号服务暂时不可用”。沙箱内 Node v22.23.3 已内置 `node:sqlite`，
`server/index.mjs` 本身就是「同一个端口发静态 + API」，因此直接把 9090 的服务从
python 换成 Node，账号功能零改动即可用，且不需要 CORS、不需要额外端口映射。

## 三、部署步骤（可复现）

在沙箱 `/data/home` 下执行（通过 `/home/user/instabox-run.js` 远程执行）：

```bash
# 1. 备份旧站（3.1MB）
tar czf site-v096-backup-$(date +%Y%m%d-%H%M).tar.gz site

# 2. 拉取最新代码（GitCode，公开仓库可匿名 clone）
rm -rf game1-v099 && git clone --depth 1 https://gitcode.com/laotongtian/game1.git game1-v099

# 3. 构建（零依赖，无需 npm install）
cd game1-v099 && node tools/build_bundle.mjs      # dist 57 个文件 / 4.1MB / bundle 857KB

# 4. 停旧服务（精确匹配，避免误杀 8080 的其它项目）
pkill -f 'http.server 9090'

# 5. 原子替换站点根
rm -rf site.new && mkdir site.new && cp -a dist/. site.new/
mv site site.old-<时间戳> && mv site.new site

# 6. 启动 Node 同源服务
mkdir -p /data/home/neon-data
nohup env NH_PORT=9090 NH_HOST=0.0.0.0 \
  NH_DB=/data/home/neon-data/game.db \
  NH_SITE_ROOT=/data/home/site \
  node /data/home/game1-v099/server/index.mjs > /data/home/neon-server.log 2>&1 &
```

**必须补一步**：`cp /data/home/game1-v099/VERSION /data/home/site/VERSION`。
`server/index.mjs` 从 `SITE_ROOT/VERSION` 读版本号，dist 不含该文件，漏掉会让
`/api/health` 返回 `"version":"unknown"`（本轮实际踩到，已修复）。

## 五、风险与注意事项

1. **没有进程守护**：当前用 `nohup` 起 Node，沙箱重启后不会自动拉起。需要长期稳定时应：
   - 写 systemd unit（若沙箱有 systemd）；或
   - 在 Instabox 控制台设置启动命令；或
   - 至少保留本节的复现命令，重启用一条命令恢复。
2. **数据在 `/data/home/neon-data/game.db`**：沙箱销毁/重建会丢。需要时先
   `node server/backup_db.mjs`（`NH_DB` 指向同一路径）备份到仓库外。
3. **端口 9090 是本项目专用**：8080 属于同沙箱另一个项目，禁止 `pkill -f 'http.server'`
   这种宽泛写法，必须带端口。
4. **旧站保留**：`site.old-<时间戳>` 与 `site-v096-backup-*.tar.gz` 均在 `/data/home`，
   确认稳定后可手动清理。
5. **HTTPS  Cookie**：当前未设 `NH_SECURE_COOKIE=1`。Instabox 外部是 HTTPS、内部是 HTTP，
   如确认网关透传 `X-Forwarded-Proto: https`，可加该环境变量提升安全性（需重启验证登录态）。

## 六、回滚

```bash
pkill -f 'server/index.mjs'
cd /data/home && rm -rf site && tar xzf site-v096-backup-<时间戳>.tar.gz
cd site && nohup python3 -m http.server 9090 --bind 0.0.0.0 > /data/home/http9090.log 2>&1 &
```

回滚后账号 API 会恢复 404，游戏本身不受影响（离线可玩）。

## 八、持久分区部署（2026-11-20 04:00 追加）

用户要求「放到持久分区」。沙箱有两块盘：

- `/dev/root` 16G 挂载 `/`：系统盘，沙箱重建会重置；
- `/dev/vdb` 20G 挂载 `/data`：数据盘（ext4），项目持久目录都在这。

项目专用持久目录是 **`/data/neon-heart`**（原本就有 `serve-loop.sh` 守护脚本）。

迁移结果：

| 项目 | 位置 |
|---|---|
| 站点根 | `/data/neon-heart`（v0.9.9，bundle 877,765 字节） |
| 服务端代码 | `/data/neon-heart/server/`（index/api/auth/db/config/backup_db/ctl） |
| 数据库 | `/data/neon-heart/data/game.db` |
| 守护脚本 | `/data/neon-heart/serve-loop.sh`（Node 同源，8081，退出 2 秒后自动拉起） |
| 旧版备份 | `/data/home/neon-heart-backup-v098-20261119-1956.tar.gz`（3.1MB） |

两个对外入口**共用同一个数据库**：

- **8081**（持久目录 + 守护循环，主入口）
- **9090**（兼容入口，同样 `NH_SITE_ROOT=/data/neon-heart`、同一 `NH_DB`）

验收：两个端口分别执行「注册 → 上传云存档 → 注销」，全部通过；库内 `users` 为空。

### 新踩的坑：SQLite WAL 未 checkpoint 时不能直接 `cp`

复制 `game.db` 后，副本里回退了已经被删除的验收账号——因为最新写入还在 `game.db-wal`
里，`cp` 只复制了主文件。正确做法：

1. 先 `PRAGMA wal_checkpoint(TRUNCATE)`；或
2. 用 `server/backup_db.mjs`（SQLite backup API）生成一致快照；
3. 迁移后核对 `users / sessions / saves` 三张表的计数。

### 常驻方式

`serve-loop.sh` 已是「Node 退出→2 秒后重启」的循环。唤醒沙箱后若地址异常，按脚本头部注释：

```bash
ss -ltnp | grep 8081
sudo fuser -k 8081/tcp
setsid nohup /data/neon-heart/serve-loop.sh > /dev/null 2>&1 < /dev/null &
```
