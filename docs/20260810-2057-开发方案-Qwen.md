## 二、架构层面问题与改进建议

### 2.1 单文件过大问题

**现状**：`app.js`（3484 行）、`engine.js`（2882 行）、`story.js`（2384 行）三个文件都超过 2000 行，维护和调试困难。

**建议拆分方案**：

```
engine.js → engine/
  ├── core.js           # PhoneEngine 主类、状态管理
  ├── time.js           # 时间推进、小时枚举、跨天
  ├── events.js         # scheduleEvent、事件分发
  ├── conversations.js  # 消息发送、选项处理、followup
  ├── calls.js          # 来电、接听、语音信箱
  ├── affection.js      # 三轴好感、关系阶段
  ├── saves.js          # 存档读写、自动存档、迁移
  ├── achievements.js   # 成就检查与解锁
  ├── daily.js          # 每日任务、连胜
  ├── dreams.js         # 梦境、梦魇
  ├── dates.js          # 约会系统
  ├── collection.js     # 收集柜、解谜
  └── watch.js          # 观赏模式

app.js → ui/
  ├── screens.js        # 屏幕切换逻辑
  ├── messages.js       # 消息界面渲染
  ├── phone.js          # 电话/来电界面
  ├── moments.js        # 朋友圈界面
  ├── album.js          # 相册界面
  ├── profile.js        # 画像/性格界面
  ├── saves.js          # 存档管理界面
  └── ...               # 每个 App 一个模块

story.js → data/
  ├── characters.js     # 角色定义
  ├── events/           # 按章节拆分剧情事件
  │   ├── prologue.js
  │   ├── day1.js
  │   ├── routes/
  │   │   ├── shenyan.js
  │   │   ├── luci.js
  │   │   ├── jiangyu.js
  │   │   └── solo.js
  │   └── endings.js
  ├── shop.js           # 商城数据
  ├── tarot.js          # 塔罗牌组
  ├── puzzles.js        # 谜题数据
  ├── collectibles.js   # 收集品
  └── ...
```

**优先级**：中等。当前单文件虽然大，但功能边界清晰，拆分可在功能稳定后逐步进行。

### 2.2 数据与逻辑耦合

**现状**：`story.js` 中的事件定义包含大量条件函数（`s => s.day >= 2`），这些函数在 JSON 序列化时会丢失，读档后需要重新注入。

**建议**：
- 将条件表达式改为声明式 DSL（如 `{condition: {day_gte: 2, affection_shenyan_gte: 3}}`），引擎侧统一解析
- 或者保持函数但建立注册表（`CONDITIONS.day2Plus = s => s.day >= 2`），读档后按名字重新绑定

### 2.3 全局状态管理

**现状**：`engine.state` 是一个深层嵌套的普通对象，各处直接修改。

**建议**：
- 引入不可变更新模式：所有状态变更通过 `engine.dispatch(action, payload)` 进行
- 好处：便于调试（可记录所有 action）、便于回放、便于测试
- 可参考 Redux 的 reducer 模式，但无需引入外部库

## 三、功能层面建议

### 3.1 剧情内容扩展

**现状**：主线剧情约覆盖 5 天（第 1 天抵达 → 路线选择 → 结局），内容量偏少。

**建议**：
- 每条路线扩展到至少 7-10 天的剧情量
- 增加更多中间事件（目前路线内的事件密度不够）
- 每位男主的闪回章节目前只有 1-2 个，可增加到 3-5 个
- 增加日常随机事件池（不同地点、不同时间段、不同好感阶段的随机对话）

### 3.2 音效与音乐

**现状**：音乐 App 存在但只有数据层面的解锁，无实际播放。

**建议**：
- 添加背景音乐（BGM）：不同时段/地点/心情切换
- 添加音效：消息提示音、来电铃声、选项点击、转场
- 使用 Web Audio API，资源放 CDN 或 base64 内嵌
- 预期资源量：BGM 3-5 首（各 1-2MB）、音效 10-20 个（各 50-200KB）

### 3.3 动画与视觉增强

**现状**：UI 以静态为主，打字效果只有简单的逐字显示。

**建议**：
- 消息气泡的弹入动画
- 屏幕切换的滑动过渡（模拟 iOS）
- 通知弹窗的弹性动画
- 好感度变化时的粒子效果（心形/星星）
- 梦魇场景的抖动/模糊特效
- 结局画面的渐入演出

### 3.4 移动端适配

**现状**：已有 viewport 限制，但未做完整的移动端适配。

**建议**：
- 添加 PWA 支持（manifest.json + service worker），可安装到手机桌面
- 触摸手势：滑动解锁、左滑删除消息、下拉刷新
- 适配不同屏幕比例（iPhone SE → iPad）
- 添加振动反馈（消息到达、选项选择）

### 3.5 数据持久化增强

**现状**：localStorage 为主，内存降级。

**建议**：
- 添加 IndexedDB 支持（容量更大、支持二进制）
- 云存档同步（可选，需要后端或第三方服务如 Firebase）
- 存档压缩（state JSON 可 gzip 到原来的 1/5）
- 多设备同步时冲突处理策略

## 四、代码质量建议

### 4.1 类型安全

**现状**：纯 JavaScript，无类型检查。

**建议**：
- 引入 JSDoc 类型注释（不改变构建流程，但 IDE 可提示）
- 关键数据结构定义类型：
  ```javascript
  /** @typedef {{closeness:number, trust:number, tension:number}} AffectionDetail */
  /** @typedef {{day:number, minute:number}} GameTime */
  ```
- 或者迁移到 TypeScript（工作量大，但长期收益高）

### 4.2 错误处理

**现状**：部分关键路径有 try-catch，但很多地方假设数据一定存在。

**建议**：
- 引擎方法统一返回 `{ok: boolean, reason?: string}` 格式（部分已这样做）
- 对 `story.js` 数据做启动时校验（schema validation）
- 添加全局错误边界，捕获未处理异常并提示用户

### 4.3 性能优化

**现状**：DOM 操作较多，每次消息都重新渲染。

**建议**：
- 消息列表使用虚拟滚动（消息量大时）
- 减少 `innerHTML` 使用，改用 `document.createElement` + 缓存
- 对频繁更新的 UI（状态栏时间、电池）使用 `requestAnimationFrame`
- 图片资源懒加载（相册、朋友圈图片）

### 4.4 可访问性

**现状**：未考虑无障碍。

**建议**：
- 所有按钮添加 `aria-label`
- 键盘导航支持（Tab 切换 App、Enter 选择）
- 颜色对比度检查（当前配色方案可能不够）
- 屏幕阅读器适配

### 5.1 当前测试覆盖

| 类型 | 数量 | 覆盖范围 |

### 5.2 缺失的测试

**建议补充**：
- **单元测试**：每个引擎模块独立测试

  - 好感度计算（三轴折算、上下限）

  - 每日任务生成与检查

  - 每条路线的完整链路（目前只测了沈砚之线）
  - 独行线 + 真结局
  - 所有约会场景
  - 所有谜题解答
- **E2E 测试**：
  - 每个 App 的打开/关闭
  - 存档导入导出流程
  - 主题切换
  - 观赏模式自动运行
- **性能测试**：
  - 大量消息时的渲染帧率
  - 长时间运行的内存泄漏检测

### 5.3 测试基础设施改进

**建议**：
- 添加测试覆盖率报告（Istanbul/c8）
- CI 中并行运行不同测试套件
- 添加视觉回归测试（Playwright screenshot comparison）
- 添加剧情数据完整性校验测试（所有事件 ID 引用存在、无死链）

## 六、部署与分发建议

### 6.1 当前部署

**现状**：纯静态文件，无构建步骤，无部署配置。

**建议**：
- 添加 `vite.config.js` 或 `webpack.config.js`（模块化后）
- GitHub Pages 自动部署（已有 GitHub Actions 基础）
- 添加版本号自动注入（构建时写入 HTML meta）

### 6.2 桌面应用打包

**建议**：
- 使用 Electron 或 Tauri 打包为 macOS/Windows/Linux 桌面应用
- Tauri 更轻量（~5MB vs Electron ~150MB）
- 可复用现有 HTML/JS/CSS，只需添加主窗口逻辑

### 6.3 移动端分发

**建议**：
- PWA 方式：最简单，添加 manifest + service worker
- Capacitor 方式：打包为原生 iOS/Android 应用
- 微信小程序：需要重写 UI 层，但引擎和数据层可复用

## 九、具体实施建议

### 9.1 剧情扩展的具体步骤

1. 先为每条路线写一份详细的大纲（每天发生什么、触发什么事件）
2. 在 `story.js` 中按大纲逐步添加事件
3. 每添加一段就运行 `test_story.js` 验证链路
4. 注意平衡各路线的内容量，避免某条线特别短

### 9.2 音效添加的具体步骤

1. 收集/制作音效资源（可用免费素材：freesound.org、pixabay.com）
2. 在 `engine.js` 中添加 `playSound(name)` 和 `playBGM(name)` 方法
3. 在关键事件触发时调用（消息到达、来电、选项选择、转场）
4. 添加音量设置和静音开关
5. 使用 `<audio>` 元素或 Web Audio API

### 9.3 模块化拆分的具体步骤

1. 先拆分 `story.js`（纯数据，风险最低）
2. 再拆分 `engine.js`（按功能域拆分，保持 PhoneEngine 为入口）
3. 最后拆分 `app.js`（每个 App 一个模块）
4. 每拆分一个模块就运行全部测试确认无回归
5. 使用 ES modules（`import/export`），添加简单的构建步骤

## 十、风险与注意事项

### 10.1 技术风险
- **localStorage 容量限制**：约 5-10MB，存档 + 收集数据可能接近上限
- **定时器泄漏**：已有 `_timers` 集合管理，但需持续注意
- **跨浏览器兼容**：目前只在 Chrome 测试，需确认 Safari/Firefox 兼容

### 10.2 内容风险
- **剧情断链**：事件之间的 `then`/`thenEvent` 引用可能遗漏
- **平衡性**：好感度增长曲线需要反复测试调整
- **成就可达性**：需确认所有成就都有合理的解锁路径

### 10.3 维护风险
- **单人开发**：代码量大，需要良好的文档和测试保护
- **存档兼容**：每次 state 结构变更都要更新 `save_migrations.js`
- **多 AI 协作**：已有 Kimi/Seed/GLM 的建议文档，注意合并冲突

---

## 十一、总结

《霓虹心事》已经是一个功能丰富的手机模拟器文字游戏，核心系统完备，测试基础设施健全。主要短板在于：

1. **内容量不足**：剧情偏短，各路线内容不均衡
2. **感官体验单一**：缺少音效、动画偏少
3. **代码规模大**：三个 2000+ 行的文件需要拆分
4. **分发渠道单一**：目前只能通过浏览器访问

建议按 P0 → P1 → P2 → P3 的顺序推进，优先补充内容和音效，再逐步优化架构和扩展平台。
